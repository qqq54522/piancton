# 卖点意图识别

把自然语言需求翻译为“体系候选 + 核心卖点 + 排除卖点 + 查询状态”，再把可信卖点交给素材关系检索。不要直接凭相似词挑图，也不要把证明点误升为新的核心卖点。

## 使用顺序

1. 第一层只读取 `SYSTEM_ROUTER_RULES.md`，根据用户原话判断主体系、最多一个相邻候选、明确多体系、纯画面或无可靠体系；此层不读取卖点目录、不判断卖点。
2. 第二层完整读取 `RULES.md`、第一层候选对应的完整 `references/sync-*.md`，以及这些体系内当前启用的卖点目录。候选超过一个时才完整读取 `references/cross-system-calibration.md`。
3. 保留用户原话，识别其中独立出现的产品能力、痛点、结果和使用场景证据，用稳定卖点 code 做内部判断；展示名称以当前项目数据库中的启用概念为准。
4. 判断查询状态：明确单卖点、明确多卖点、探索型、待消歧、纯画面或无可靠卖点。
5. 单独提取显式否定，不得把“不要、无需、排除”的卖点同时当成正向命中。
6. 输出可解释的判断理由。只有话术中的独立证据才允许产生 `direct` 命中；相邻或弱关联卖点降为 `related`/候选。
7. 第三层只在已接受的卖点—素材关系集合内，以已采纳素材独有话术承担主筛选，标题和 V3 画面事实/场景只作辅助。已有 `expresses` 直接素材时，只有 `supports` 的证明图必须命中 accepted 图片话术或被查询明确点名标题/画面证据；没有对应图片时返回空，不用全局语义相似度补一张无关图片。

## 公共话术优化

六大体系、16 个核心卖点、稳定 code、主体系归属和体系文件中的已确认边界是冻结层。优化公共话术时只能在冻结层上增加“语言入口”，不得增加卖点、移动归属或改写卖点含义。

1. 先读取 `references/selling-point-map.json` 固定目标 code，再读取 `references/public-phrase-governance.json` 的入口规则和评测用例。
2. 区分三类输入：熟悉业务的人会直接说卖点或功能别名；了解一点的人会说对象、动作和目的；业务小白通常只会说痛点、担忧或想要的结果。
3. 只有能脱离上下文、稳定且唯一指向一个既有 code 的表达才进入公共话术。每轮每个卖点至多新增一条，先查重、再查跨卖点冲突。
4. 小白长句、情境变体和大量口语优先作为理解样例与评测用例，由本 Skill 根据对象、动作、时间尺度、目的和执行主体归一化；不要把每个句子复制进数据库。
5. 共享短词标为整句探索或待消歧；宽泛结果保持无可靠卖点。不得为了提高命中率把“提分、学习不好、跟不上、省心”等词硬塞给某一个卖点。
6. 评测样例不是公共话术。只有 `approvedAdditions` 中通过审核的表达才允许进入当前种子和数据库；增加或删除候选必须同时更新校验用例。

## 知识文件

- `references/sync-school.md`：同步校内体系。
- `references/sync-exam.md`：同步考点体系。
- `references/sync-cultivation.md`：同步培养体系。
- `references/sync-planning.md`：同步规划体系。
- `references/sync-self-study.md`：同步自学体系。
- `references/sync-companion.md`：同步伴学体系。
- `references/cross-system-calibration.md`：六大体系共享入口、相邻边界和多意图校准。
- `references/selling-point-map.json`：页面精简卖点名称、稳定 code、主体系与 Skill 完整业务名称的一一对应表；核对目录或数据库时必须读取。
- `references/public-phrase-governance.json`：公共话术受控新增、共享入口、非路由表达和专家/了解者/小白三档自然语言评测；优化公共话术时必须读取。
- `references/output-contract.md`：结构化输出与判定规则。
- `SYSTEM_ROUTER_RULES.md`：在线第一层六大体系路由；不得混入卖点目录。
- `RULES.md`：在线第二层完整输出协议、判断边界和素材关系约束；不得混入非候选体系。

只读取完成当前任务所需的体系文件；一旦某个体系被选为候选，就必须完整读取该体系文件，不得只抽取摘要、关键词或局部段落。按需加载是缩小体系范围，不是压缩体系知识。维护某个体系时同样必须完整读取该体系文件。六个体系未全部梳理完成前，状态为“待梳理”的文件不能被当作完整事实来源。

## 知识层级

```text
稳定体系
  └─ 核心卖点
       └─ 证明点
            └─ 证据表达点（原脑图绿色制作文字）
                 └─ 已审核素材关系
```

- 六大体系是稳定业务地图，不是每次搜索的唯一硬过滤条件。
- 页面可以使用精简卖点名称，但必须通过 `selling-point-map.json` 中的稳定 code 唯一对应本 Skill 的完整业务含义；名称相似不能代替 code 对应。
- 核心卖点必须来自业务原版或经业务确认的变更，不能为了提升召回自行新增。
- 证明点解释卖点为什么成立，可以跨卖点复用；专家、功能、数据、案例、证书和效果材料通常是证明点，不自动成为核心卖点。
- 痛点、结果、场景和口语用于识别意图，不反向改写产品事实。
- 原始脑图中的绿色文字作为证明点下的证据表达点参与搜索理解和人工筛选；它是作图依据，不是已验证产品事实，也不代表对应素材已经存在。

## 判断边界

- 一句话确实包含多个独立需求时保留多个卖点，通常不超过四个；不要强行选唯一赢家。
- 只输入体系名或共享入口词时输出探索型，让多个候选并列，不伪装成明确多卖点。
- “提分、跟不上、学习不好”等宽泛结果没有足够证据时，输出待消歧或无可靠卖点。
- 纯颜色、版式、人物、场景等视觉要求属于纯画面查询，不强绑业务卖点。
- 用户给出新事实、数字、学校、媒体、证书或效果结论时，先标记待核验，不能直接写入稳定知识。

## 项目内自动调用

当前项目通过 `backend/app/ai/skill_loader.py` 渐进加载本 Skill：先只加载 `SYSTEM_ROUTER_RULES.md`；命中候选体系后，再完整加载 `RULES.md`、候选体系原文件和候选体系内数据库目录，候选超过一个时才完整加载跨体系校准。禁止一次把六个体系和全部卖点注入在线查询，也禁止把已命中的体系改成摘要版再判断。数据库当前启用卖点、名称、定义和已采纳/拒绝话术是运行时权威；本 Skill 提供跨任务复用的语义、边界和业务原版底稿。

完整输出字段和查询状态定义见 `references/output-contract.md`。
