# 卖点智库项目阶段汇报（当前改版版）

汇报日期：2026-09-22  
项目名称：卖点智库 / Piancton  
汇报口径：以当前代码、`docs/IMAGE_SEARCH_REBUILD_MASTER_PLAN.md` 和本地最新验收记录为准。旧版结项材料只作为结构参考，不作为当前事实来源。

## 0. 先说结论

这次改版的核心，不是继续给图库增加更多标签，而是把系统改造成一条“业务语言 → 业务概念 → 人工确认素材关系 → 可解释结果”的完整链路。

当前项目已经完成 Phase 0～Phase 6 的核心工程改造，并形成了可使用的素材管理、业务概念治理、自然语言搜索、素材库 Agent、渠道整理和账号体验闭环。当前本地基线包括：

- 6 个稳定业务体系、16 个核心业务概念；
- 40 个素材组、40 张图片；
- 55 条人工 accepted 素材关系；
- 图片身份码、主图与延展版本、渠道和分类目录管理；
- 业务端一个搜索框，设计师端负责素材与业务关系维护；
- 在线 AI 统一使用火山 Viking AI Search，失败时由本地确定性能力降级；
- 素材库 Agent 可以围绕业务知识、图片和已确认关系进行自由问答与找图。

但项目还不能简单说成“搜索质量已经最终验收完成”。原因是当前真实素材和人工关系规模仍在持续建设，Phase 0/4 的搜索效果需要重新用更完整的代表图片、证明点和真实业务查询建立基线；本地最新改动也尚未全部部署到云端。

## 1. 项目回顾：这次真正要解决什么问题

### 1.1 原来的问题不是“没有搜索框”，而是业务事实没有被组织起来

普通图库可以通过文件名、关键词或视觉相似度找图，但卖点素材库面对的是另一类问题：业务人员往往说的是“想体现专家背书”“找一个孩子一看就懂的动画图”“想要课后马上练习的素材”，而不是图片标题。

因此系统需要同时回答三个问题：

1. 用户这句话真正想表达哪个业务卖点？
2. 哪些图片经过负责人确认，确实可以表达或支撑这个卖点？
3. 同一个卖点下，哪张图片最贴近当前使用场景和表达重点？

旧式“图片 + 固定标签 + 相似度”的方案无法稳定回答这三个问题，容易出现画面看起来相似、业务含义却不准确的结果。

### 1.2 改版后的项目目标

新版目标可以概括为：

> 让业务人员用自己的话找素材，让系统用业务概念理解需求，让负责人确认的关系决定素材是否可用，让每个结果都能解释为什么匹配。

项目的核心原则已经从“尽量多召回”转为：

- 六大体系是稳定业务地图，不是所有搜索的硬过滤条件；
- 业务概念可以版本化，图片和概念采用多对多关系；
- 一张图片可以主要表达一个概念，同时支撑其他概念；
- AI 可以提出理解和建议，但不能绕过人工确认直接制造业务事实；
- 没有可信业务关系时，宁可返回空结果，也不拿无关图片补位；
- 普通业务用户只使用一个搜索框，不要求理解“精准/智能”等内部模式。

### 1.3 当前形成的完整业务链路

```text
设计师上传主图
  → 建立素材组和图片版本
  → 人工选择渠道、场景等事实
  → 维护业务概念关系和搜索话术
  → 负责人确认“主要表达 / 可以支持 / 不适用”
  → 业务人员用自然语言搜索
  → AI Search 理解业务意图
  → 本地按 accepted 关系核对素材事实
  → 返回素材卡、尺寸/版本和匹配原因
  → 发送给 Agent、收藏、复制身份码或下载
  → 通过搜索日志、反馈和真实查询继续调优
```

## 2. 最终交付了什么

### 2.1 面向业务人员的使用能力

业务人员现在可以：

- 只通过一个搜索框输入自然语言；
- 不需要先学习 16 个卖点名称，也不需要手动选择搜索模式；
- 可选使用六大体系筛选，但体系筛选不是默认强制步骤；
- 查看按素材组整理的搜索结果，选择可用的图片尺寸或版本；
- 查看当前图片为什么匹配本次搜索；
- 通过图片身份码进行确定性精确查找；
- 把图片发送给素材库 Agent，继续询问“这张图怎么讲、适合什么场景、还有没有同类素材”；
- 收藏到项目夹、复制身份码、预览和下载。

### 2.2 面向设计师和素材负责人的维护能力

设计师侧已经从“上传图片”扩展为“维护可用素材事实”：

- 首次上传主图后自动建立素材组，业务概念和延展尺寸不是首次上传必填项；
- 支持主图、延展尺寸、备选图和修订版本；
- 可以在素材详情中追加版本、替换主图和回收非主图版本；
- 维护图片所属渠道、场景/功能属性和目录归属；
- 维护图片与业务概念的主要表达、可以支持和不适用关系；
- 管理公共话术继承与素材独有话术；
- 可在渠道分类内原地调整图片；
- 可复制渠道分类结构，也可定点复制某个分类及其子树；
- 删除目录时只解除目录绑定，不删除图片文件和素材记录。

### 2.3 六大体系与业务知识交付

项目已经把原始业务截图整理为可治理的知识结构：

| 业务体系 | 核心卖点数量 | 当前作用 |
| --- | ---: | --- |
| 同步校内 | 3 | 教材版本与课程目录、动画讲透、学练测闭环 |
| 同步考点 | 3 | 新课标新考法、专项培优、理解原理举一反三 |
| 同步培养 | 3 | 专家设计、学段衔接、底层方法与思维 |
| 同步规划 | 1 | 根据个人情况形成学习计划与路径 |
| 同步自学 | 4 | AI 答疑、拍题精学、预习复习、AI 错题本 |
| 同步伴学 | 2 | 真人老师督学、学情报告反馈 |
| 合计 | 16 | 以稳定 code 连接知识、素材关系和评测 |

证明点和原图绿色证据表达点被保留为更细的治理与素材依据，但不自动等于已经核验的产品事实，也不自动等于系统中已经存在对应图片。

当前 AI Search 的 `chat_search` 不是只连接一份知识，而是同时使用两层业务知识文档，并结合图片素材数据：

1. **体系知识文档**：说明六大体系的定义、边界和体系级路由。
2. **卖点知识文档**：说明 16 个核心卖点的定义、搜索语言、证明点、相邻卖点和判断规则。
3. **图片素材数据集**：这是独立的图片物品数据，不属于业务知识文档，承载当前已发布图片的标题、图片唯一 ID、预览地址、业务文本和可检索字段。

两层业务知识文档帮助 AI Search 理解用户问题，图片素材数据集帮助它找到候选图片；最终图片是否能作为正式结果，仍需回到 Piancton 本地数据库核对人工 accepted 关系。也就是说，AI Search 负责“理解和找候选”，本地系统负责“确认业务事实和返回真实图片”。

### 2.4 当前系统结构

当前系统可以按五层理解：

```text
使用层：业务搜索 / 设计师素材维护 / 素材库 Agent
知识层：六大体系 / 16 个业务概念 / 证明点与搜索语言
事实层：素材组 / 图片版本 / 渠道目录 / 人工 accepted 关系
搜索层：AI Search 意图理解 + 本地关系约束 + 数据库/可选索引召回
治理层：权限 / 审计 / 日志 / 行为反馈 / 部署与备份验收
```

代码层面继续保持 API、Service、Domain、Repository、Storage 和 Search Backend 的边界。Meilisearch 只是可重建的增强索引，不是素材和业务关系的事实源。

在线链路可以进一步简化为：

```text
用户问题
  → 火山 AI Search
      ├─ 体系知识文档：识别六大体系
      ├─ 卖点知识文档：识别 16 个卖点及边界
      └─ 图片素材数据集：检索候选图片
  → Piancton 本地数据库
      ├─ 核对图片是否真实存在且已发布
      ├─ 核对人工 accepted 关系
      └─ 返回真实素材卡和匹配解释
```

## 3. 实际效果：现在业务可以怎么用

### 3.1 业务人员可以用自然语言找业务素材

用户不必输入标准卖点名称。例如：

| 用户说法 | 系统应理解的方向 | 结果边界 |
| --- | --- | --- |
| “想找体现专家背书的图” | 专家设计、专家团队或相关证明点 | 只返回已确认关系和话术能够支撑的素材 |
| “孩子一看就懂的动画课画面” | 动画讲透知识点 | 不把普通人物图或纯视觉动画当作业务素材 |
| “学完马上练几道确认一下” | 学练测闭环 | 优先匹配有即时练测表达的素材 |
| “孩子不会的题，先讲思路别直接给答案” | 拍题精学 | 不把“直接给答案”误当正向卖点 |
| “想找适合小升初过渡的素材” | 学段衔接 | 不用普通校内同步图替代衔接证据 |

如果用户只说“提分”“学习不好”“家长省心”等宽泛结果，系统可以保持待消歧或探索状态，不强行把它归到某一个卖点。

### 3.2 搜索结果为什么更可信

新版搜索不是让模型直接决定图片，而是分成三步：

1. AI Search 负责理解用户语言，识别体系、卖点、证明点或查询状态。
2. 本地业务数据负责核对图片是否存在人工 accepted 的 `expresses` / `supports` 关系。
3. 本地规则和结果编排负责过滤、排序、去重、解释和降级。

因此，模型可以帮助系统“听懂用户”，但不能越过负责人确认，直接把一张相似图片变成业务事实。可信素材不足时返回空结果，本身也是系统正确行为。

### 3.3 素材库 Agent 带来的效果

素材库 Agent 已经从固定的“问题分析”工具改为普通自由问答入口。它可以帮助用户：

- 解释图片可见内容；
- 结合已确认的业务概念和素材话术解释“为什么适合”；
- 根据自然语言继续找图；
- 返回可点击的真实素材卡，而不是只返回模型生成的名称；
- 继续追问当前图片、历史问题或上一轮找图结果；
- 在业务知识问题上参考当前项目六大体系，而不是套用外部同名体系。

图片发送采用一次性附件边界：问图成功后消费待发送图片，后续追问沿用会话语境，但不声称每一轮都重新读取原始像素。在线视觉问答能否真正读取图片，还依赖云端配置可访问的公网图片桥，本地回环地址不能作为最终验收依据。

### 3.4 素材身份码带来的效果

当前身份码定位的是一张活动图片，而不是一个容易变化的素材组概念。标题修改、渠道调整或版本变化不会让业务人员只能凭文件名重新寻找；输入身份码时直接走确定性查找，不进入语义搜索。

它适合用于：

- 在群聊、文档或汇报中准确指向一张图片；
- 区分同一素材的不同尺寸或版本；
- 复盘下载、分享和使用记录；
- 避免模型把相似名称误认为同一素材。

### 3.5 单一 AI Search 在线入口带来的效果

当前首页搜索、推荐、补全、行为闭环和素材库 Agent 问答都调用火山 Viking AI Search。AI Search 的在线问答同时使用两层业务知识文档——体系文档、卖点文档——并检索图片素材数据集；不是只调用一个空的通用大模型，也不是只在本地数据库里查图片。旧 API 中心、通用模型 Provider、独立 Embedding/Reranker、旧 VikingDB 路由和上传时自动图片分析已经退出当前运行时。

这样做的重点不是减少页面，而是让在线链路更容易解释和验收：

- 在线语义能力只有一个主要入口；
- 体系文档、卖点文档和图片素材数据在同一 AI Search 应用中协同工作；
- 本地数据库和人工关系仍掌握业务事实；
- AI Search 不可用时可以使用本地确定性降级；
- 日志和错误边界更清楚；
- 不把每个功能拆成一套互相独立的 Key、模型和 Prompt。

## 4. 问题与复盘

### 4.1 为什么没有继续采用传统图库式搜索

传统图库擅长找“画面上有什么”，但本项目要找的是“这张图能不能代表某个业务表达”。

例如搜索“专家背书”，仅凭人物、证书或蓝色背景无法证明它真的表达专家设计；搜索“动画讲透”，仅凭动态图形也无法证明它讲的是知识点。业务关系和人工确认必须成为结果准入的一部分。

### 4.2 为什么不能让模型直接决定结果

模型适合做语义理解，不适合直接替企业确认产品事实。直接让模型从全库挑图会带来：

- 同一句话在不同时间返回不同结果；
- 相邻卖点之间容易串线；
- 未确认的证明材料被误当成已确认事实；
- 结果无法说明是因为业务关系命中，还是因为视觉相似；
- 出现空结果时无法判断是没有素材、没有关系，还是模型失败。

新版把模型的职责限制在理解和候选生成，把事实准入、权限、存储、关系、排序和降级留在可测试的本地服务中。

### 4.3 为什么必须保留人工工作关系

负责人确认“主要表达 / 可以支持 / 不适用”不是图片质量评分，而是搜索金标准。它回答的是：

> 这张图片在业务上是否真的能用于表达这个概念？

人工工作不是为了和 AI 竞争，而是为 AI 提供可靠边界。模型可以辅助整理、提议和解释，但只有人工确认后的关系才能进入正式业务搜索主通道。

### 4.4 为什么不再把 API 调度中心作为当前产品重点

早期阶段需要 API 中心来验证多 Provider、模型能力、健康检查和调度策略；但在当前改版中，继续保留它会让运行时边界重新变复杂，也容易让汇报误以为系统需要多个模型池才能工作。

因此新版选择：

- 在线 AI 统一使用 AI Search；
- 历史 API 中心表和迁移只为旧库无损升级保留；
- 当前页面、接口、Worker 和业务消费者不再依赖旧 API 中心；
- 以后如确有新的在线模型治理需求，必须先新增决策和验收边界，不能直接恢复旧链路。

### 4.5 为什么不重新固化成唯一的二级标签树

图片可能同时服务多个业务概念，同一个概念也可能由多张图片分别承担主要表达、证明支撑或场景补充。如果把所有内容压成一棵唯一标签树，后续会出现：

- 一张图只能挂一个地方；
- 证明点被误当成核心卖点；
- 业务概念一变化就要迁移大量图片；
- 搜索结果无法表达“主要表达”和“可以支持”的差别。

当前采用版本化概念和多对多关系，保留业务变化空间。

### 4.6 当前仍需正视的问题

- 素材规模和人工关系还没有覆盖全部证明点，部分查询没有素材是数据缺口，不是搜索代码一定失败。
- 当前本地最新代码与云端部署版本存在阶段差异，不能把本地已完成能力直接说成线上已验证。
- Agent 的真实视觉问答需要公网图片桥和云端环境验收，本机 `localhost` 地址无法被火山服务读取。
- 搜索历史评测是在不同阶段数据上完成的，必须用当前 40 个素材组和新增关系重新建立可比较基线。
- 全量类型治理和长期运维验收仍需继续，不能只用一次前端构建成功代替生产验收。

## 5. 后续规划

### 5.1 补齐真实素材闭环

优先导入代表性主图，完成每张图的：

- 业务概念关系确认；
- 证明点和证据表达点归属；
- 渠道与使用场景确认；
- 素材独有搜索话术；
- 主要表达、可以支持、不适用边界。

目标不是单纯增加图片数量，而是让每一组重要业务表达都有可核验的素材承载。

### 5.2 重新建立搜索质量基线

使用真实业务查询重新评测：

- 意图识别是否正确；
- 主要表达素材是否进入前列；
- 多卖点是否都被覆盖；
- 显式排除是否生效；
- 没有可信素材时是否诚实返回空；
- 平均延迟、P95 延迟和降级提示是否可接受。

搜索优化顺序保持为：先修正业务概念和关系，再优化话术与召回，最后才调整排序和性能。

### 5.3 完善证明点和话术治理

继续把真实搜索日志里的新说法分成三类：

- 可以稳定指向已有卖点的公共话术；
- 只适合某张图的素材独有话术；
- 需要进入评测集、但不能直接写入词库的模糊表达。

对于数字、学校、奖项、媒体、成绩和覆盖率等证明材料，先核验来源、时间和口径，再决定是否进入可用素材关系或对外解释。

### 5.4 完成云端发布和生产验收

下一步需要针对当前本地最新版本完成：

- 云端代码和数据库迁移升级；
- AI Search 图片与知识数据集配置；
- 公网图片桥与真实视觉问答验证；
- 权限、上传、搜索、预览、下载、反馈闭环验收；
- HTTPS、持久化卷、PostgreSQL 备份恢复演练；
- 记录部署版本、回滚点和线上健康状态。

在这些事项完成前，项目状态应表述为“工程改造完成，生产闭环持续验收”，而不是“生产环境全部验证完成”。

### 5.5 观察 Agent 和行为反馈的实际价值

持续观察：

- 用户在搜到图片后最常追问什么；
- 哪些图片经常被要求解释但缺少素材话术；
- 哪些查询反复无结果；
- 哪些结果被下载、收藏或继续追问；
- Agent 是否帮助新人减少二次确认，而不是制造新的错误事实。

这些行为应反过来指导素材补齐、关系确认和话术治理，而不是直接把模型回答写成新的业务事实。

## 6. 汇报时可以用的一句话

> 这次改版把卖点智库从“存图片、加标签、靠相似度找图”，升级成了“用业务知识组织素材、用 AI 理解自然语言、用人工确认保证业务正确、用 Agent 帮助理解和使用素材”的内部业务素材基础设施。

当前工程骨架和核心链路已经完成，下一阶段的重点不再是继续堆功能，而是用更多真实素材、真实关系和真实搜索日志，把“能运行”持续验证成“业务人员愿意依赖”。
