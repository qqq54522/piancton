# AI 图片打标与混合检索架构

更新日期：2026-06-24

> 2026-06-24 备注：第一轮已经实现数据库默认搜索与 Meilisearch 可选降级层、
> 搜索文档生成、增量同步和重建索引脚本。当前业务事实源仍是数据库；
> Meilisearch 只作为可选增强层和派生索引，是否在服务器启用以部署验收为准。

## 1. 产品目标

Piancton 的目标不是制作一个普通图片管理器，而是让业务人员即使不知道标准标签、只输入一个词、一句口语化需求或不完整描述，也能找到适合使用的图片。

图片上传时可以完全没有标题。系统需要主要依靠：

- 设计师明确指定的业务归属；
- 图片本身的视觉内容；
- 图片中的文字；
- 六大体系及其二级业务概念；
- AI 对图片的业务适用性判断；
- 内容语义向量；
- 可解释的搜索排序。

系统必须同时支持：

- 本地 SQLite 开发；
- 部署后的 PostgreSQL；
- OpenAI、Gemini、DeepSeek、专用 OCR、Embedding、Reranker 等不同第三方 API；
- 后续更换模型而不重建整个业务层。

## 2. 核心判断

### 2.1 设计师标签和 AI 标签可以同时成立

设计师选择的标签代表“这张图片原本为哪个业务卖点设计”，AI 建议代表“从画面证据看，这张图片还适合哪些业务表达”。

例如：

```text
设计师主标签：
同步自学体系 > AI拍题精学

AI 建议：
同步培养体系 > 万能解法
同步自学体系 > AI私教答疑
```

系统不应让 AI 覆盖设计师，而应分别保存来源：

| 类型 | 含义 | 默认搜索权重 |
|---|---|---:|
| 人工主标签 | 图片原始设计意图 | 1.00 |
| 人工附加标签 | 设计师确认的其他用途 | 0.95 |
| 已接受的 AI 建议 | 设计师认可的跨体系适用性 | 0.90 |
| 未审核 AI 建议 | 模型推断，仍可能有误 | 0.60 |
| 开放内容标签 | 图片中可观察到的内容 | 按置信度计算 |

这些权重是初始值，最终应由搜索评测数据校准。

### 2.2 隐性标签不是另一棵业务标签树

隐性标签主要描述图片本身，例如：

- 人物：学生、家长、老师；
- 场景：居家学习、在线课堂；
- 物体：平板、试卷、手机；
- 动作：拍题、查看报告、视频学习；
- 界面文字：正确率、学习时长、错题；
- 风格：科技感、插画、真实摄影；
- 情绪：放心、焦虑、专注；
- 构图：横版、留白、人物居中；
- 色彩：蓝紫、暖色、浅色背景。

它们帮助搜索“蓝色科技感、有家长看报告的图”，但不能替代六大体系的业务标签。

### 2.3 最先进的大模型不是完整的搜索算法

大模型适合：

- 理解自然语言；
- 分析图片；
- 输出结构化判断；
- 扩展同义表达；
- 对少量候选做精细重排。

大模型不应单独负责：

- 全库逐张比较；
- 权威标签约束；
- 稳定去重；
- 分页；
- 过滤；
- 最终分数计算；
- 历史结果复现。

因此系统采用“模型理解 + 多路召回 + 确定性融合 + 可选重排”。

## 3. 供应商中立的 Provider 设计

### 3.1 第一版只要求一个多模态 API

下面的五类 Provider 是长期边界，不代表第一版必须找到五家 API。

第一版只要求一个支持图片输入、中文理解和 JSON 输出的多模态模型，由它同时承担：

- 图片理解；
- 主要文字读取；
- 业务标签建议；
- 复杂查询理解。

专用 OCR、Embedding 和 Reranker 都是可选增强。缺少这些增强时，系统仍可使用
六大体系目录、大模型查询扩展和 Meilisearch 中文全文搜索运行。

不要继续使用一个 `ModelProvider` 承担所有任务。建议拆成五类能力：

```text
VisionProvider
  图片 -> 视觉摘要、人物、场景、物体、动作、风格、业务证据

OcrProvider
  图片 -> 文字块、置信度、位置

QueryUnderstandingProvider
  搜索文本 -> 标准化查询计划

EmbeddingProvider
  文本或图片 -> 向量

RerankProvider
  查询 + 少量候选 -> 相关性分数与理由
```

一个供应商可以实现多种能力，也可以混合使用：

```text
视觉模型 A       -> 图片分析
专用 OCR B       -> 中文文字提取
文本模型 C       -> 搜索理解
Embedding D      -> 语义向量
Reranker E       -> Top 50 精排
```

DeepSeek 等文本模型可以负责搜索理解，但不应被强制承担图片分析；视觉模型也不必承担 Embedding。

建议环境变量按能力拆开：

```env
VISION_PROVIDER=
VISION_MODEL=
VISION_BASE_URL=
VISION_API_KEY=

OCR_PROVIDER=
OCR_MODEL=
OCR_BASE_URL=
OCR_API_KEY=

QUERY_PROVIDER=
QUERY_MODEL=
QUERY_BASE_URL=
QUERY_API_KEY=

EMBEDDING_PROVIDER=
EMBEDDING_MODEL=
EMBEDDING_BASE_URL=
EMBEDDING_API_KEY=

RERANK_PROVIDER=
RERANK_MODEL=
RERANK_BASE_URL=
RERANK_API_KEY=
```

密钥只存在后端环境变量或部署平台的 Secret 中，永远不进入浏览器和数据库。

## 4. 图片上传与打标流程

### 4.1 上传前

设计师只需要：

1. 选择一张或多张图片；
2. 选择一个人工主标签；
3. 可选选择人工附加标签；
4. 点击“上传并 AI 分析”。

标题不再必填。系统可以用文件名临时展示，但不能依赖标题检索。

### 4.2 后台分析

```text
保存图片
  -> 生成文件哈希
  -> 创建分析任务
  -> OCR
  -> 视觉理解
  -> 对照权威业务概念目录
  -> 生成 AI 二级标签建议
  -> 生成结构化内容标签
  -> 生成检索文本
  -> 生成文本向量
  -> 可选生成图片向量
  -> 建立全文和向量索引
```

部署环境不应让上传请求一直等待模型。建议增加数据库任务表和独立 worker：

```text
Web API -> analysis_jobs -> AI Worker -> 保存分析结果与索引
```

本地开发可以使用同一套任务结构，由本地 worker 执行；数据量小时也可以提供同步调试模式。这样部署后不需要推翻流程。

### 4.3 AI 输出

AI 分析结果应拆成：

```json
{
  "caption": "客观描述图片可见内容",
  "ocr_text": ["正确率 92%", "本周学习报告"],
  "visual_attributes": {
    "people": [],
    "scenes": [],
    "objects": [],
    "actions": [],
    "styles": [],
    "colors": [],
    "composition": [],
    "emotions": []
  },
  "business_suggestions": [
    {
      "label_code": "learning_report",
      "confidence": 0.91,
      "evidence_level": "A",
      "reason": "画面直接出现正确率、学习时长和掌握情况"
    }
  ],
  "negative_concepts": [],
  "search_phrases": []
}
```

模型只能返回权威目录中的 `label_code`，不能创造新业务标签。

内容标签数量不必强制为 18–22 个。应按图片内容生成，避免为凑数量制造重复或低价值词。

### 4.4 上传界面建议

上传弹窗改成三个区域。

#### A. 图片与业务归属

- 图片预览；
- 人工主标签，必选；
- 人工附加标签，可选；
- “上传并 AI 分析”按钮；
- “仅上传，稍后分析”按钮。

#### B. AI 分析状态

状态显示：

- 等待分析；
- OCR 中；
- 图片理解中；
- 正在建立检索索引；
- 分析完成；
- 分析失败，可重试。

#### C. AI 建议审核

分析完成后展示：

```text
人工主标签
[AI拍题精学]  人工确认

AI 建议的其他用途
[万能解法 87%]  接受 / 忽略
[AI私教答疑 73%] 接受 / 忽略

判断依据
画面出现拍题入口、逐步讲解和底层解题逻辑。

图片可检索内容
学生 / 手机 / 拍题 / 数学题 / 分步讲解 / 蓝色科技感
```

AI 建议可以跨体系。未审核建议仍可用于低权重召回，但前端应明确标记“AI 未确认”。

## 5. 检索文档

每张图片需要生成一份专门供检索使用的语义文档，而不是仅搜索零散标签。

示例：

```text
人工业务归属：同步自学体系，AI拍题精学。
人工附加用途：无。
AI建议用途：万能解法、AI私教答疑。
画面：学生使用手机拍摄数学题，界面展示分步推导和动画讲解。
文字：拍题精学、解题思路、相似题。
对象和动作：学生、手机、试卷、拍题、查看讲解。
风格：蓝紫色科技感教育产品界面。
适合表达：拍题后逐步理解、不是直接给答案、理解底层逻辑。
不适合表达：真人老师督学、学习周报。
```

需要分别保留字段来源，不能只保存拼接后的文本。拼接文本主要用于全文索引和 Embedding。

每次目录、Prompt、模型或 Embedding 模型变化时，记录 `index_version`，支持批量重新索引。

## 6. 业务搜索理解

### 6.1 输入形式

业务人员只看到一个主搜索框，可以输入：

- 标准标签：“动画精讲”；
- 单词：“家长放心”；
- 简短需求：“蓝色科技感学习图”；
- 完整句子：“想找一张孩子拍题后不是直接给答案，而是一步步讲明白的图”；
- 带排除条件：“学习报告，但不要真人老师”。

### 6.2 查询计划

搜索理解模型不直接返回图片，而是返回查询计划：

```json
{
  "normalized_query": "拍题后分步讲解解题思路",
  "taxonomy_candidates": [
    {"label_code": "photo_learn", "weight": 1.0},
    {"label_code": "universal_method", "weight": 0.72}
  ],
  "visual_requirements": ["手机", "题目", "分步讲解"],
  "text_requirements": [],
  "style_requirements": [],
  "outcome_requirements": ["理解解题思路"],
  "exclude_concepts": ["直接给答案"],
  "query_mode": "business_and_visual",
  "confidence": 0.88
}
```

单个标准标签或已知别名可以不调用大模型，直接命中目录。句子、模糊表达和多条件查询再调用搜索理解模型，以降低延迟和费用。

常见查询结果应缓存。

## 7. 多路召回算法

查询计划生成后，由 Meilisearch Community Edition 作为统一的派生搜索引擎，
在同一索引中执行关键词、过滤和向量召回。SQLite / PostgreSQL 仍是权威主数据。

### 7.1 业务标签召回

- 人工主标签；
- 人工附加标签；
- 已接受 AI 标签；
- 未审核 AI 标签；
- 标准标签别名；
- 30 个文案卖点到 16 个图片标签的映射。

### 7.2 全文召回

搜索：

- OCR；
- 视觉摘要；
- 内容标签；
- 搜索短语；
- 业务概念档案；
- 文件名和可选标题。

Meilisearch 负责中文分词、前缀、错字容忍和字段相关性。业务标准 code、
人工确认状态等字段仍由应用生成和约束。

### 7.3 向量召回

用查询向量匹配图片的检索文档向量。向量默认由后端的 `EmbeddingProvider`
生成后写入 Meilisearch，避免搜索引擎绑死某个供应商。可选增加图片视觉向量，
处理“找一张和这张视觉上相似的图”。

### 7.4 结构化过滤

对体系、标签、图片类型、色彩、构图、人物、横竖版等进行过滤。

### 7.5 排除召回

如果查询包含“不要真人老师”“不是直接给答案”，对应概念命中时必须扣分或过滤。

## 8. 融合排序与精排

关键词与语义结果先使用 Meilisearch 的混合排序，并通过 `semanticRatio`
调节语义搜索占比。体系、人工主标签、审核状态和排除项再由应用层作为过滤和
业务加权条件。

Top 50 再进入精排：

```text
专用 Reranker 或高能力模型
输入：查询计划 + 候选图片检索文档
输出：最终相关性、命中原因、违反的排除条件
```

最终分数还应加入：

- 人工主标签加权；
- AI 建议审核状态；
- 排除项惩罚；
- 低置信度惩罚；
- 相同图片或近似图片去重；
- 结果多样性。

不要让高能力大模型逐张扫描整个图片库。它只处理召回后的少量候选。

## 9. 本地与部署的一致性

### 9.1 本地开发

建议：

- 数据库：SQLite；
- 搜索：本地 Meilisearch Community Edition 单二进制；
- 全文、过滤和向量索引均由 Meilisearch 管理；
- AI：调用配置好的第三方 API；
- 任务：数据库任务表 + 本地 worker。

搜索服务不可用时，后端降级到现有 SQL 模糊搜索。项目提供固定版本的本地
安装检查、启动和健康检查脚本，但不把平台相关二进制提交到仓库。

### 9.2 部署环境

建议：

- 数据库：PostgreSQL；
- 搜索：固定版本的 Meilisearch Community Edition 容器；
- AI Worker：独立容器；
- 可选 Redis：只在任务量和并发提高后引入；
- 图片：持久化 volume，后续可替换对象存储。

Meilisearch 不直接暴露公网端口，只允许 backend 访问并使用 Master Key。
Service、Provider 和索引文档在本地与部署保持一致，只改变服务地址和运行方式。

## 10. 可靠性、成本与隐私

### 10.1 模型路由

不需要每一步都使用最贵模型：

- 图片业务理解：高能力视觉模型；
- 密集中文文字：专用 OCR；
- 单个标准词：目录直接匹配；
- 模糊句子：高能力文本模型；
- 向量：专用 Embedding；
- Top 50 精排：专用 Reranker 或模型。

### 10.2 缓存与去重

- 根据图片 SHA-256 避免重复分析；
- 根据模型、Prompt 和目录版本缓存分析；
- 根据标准化查询缓存查询计划；
- Embedding 只在检索文本变化时重算。

### 10.3 降级

- 查询模型失败：全文 + 向量搜索；
- Embedding 服务失败：标签 + 全文搜索；
- Reranker 失败：使用 RRF 排名；
- OCR 失败：使用视觉模型摘要；
- 某一供应商失败：按配置切换备用 Provider。

### 10.4 第三方数据边界

部署前必须确认：

- 图片是否允许发送到第三方；
- API 是否保留请求数据；
- 是否需要国内区域或私有部署；
- 日志中不得记录 API Key；
- 是否需要对图片、OCR 和用户查询脱敏。

## 11. 评测体系

没有评测集，就无法知道搜索是否真的精准，也无法判断哪个模型更好。

建议由真实业务人员准备至少 100–300 条查询，覆盖：

- 标准标签；
- 同义词；
- 用户痛点；
- 完整句子；
- 错别字和口语；
- 多条件；
- 排除条件；
- 纯视觉要求；
- 跨体系表达。

每条查询标注：

- 必须出现的图片；
- 可以出现的图片；
- 不应出现的图片。

核心指标：

- Recall@20：正确图片是否被召回；
- nDCG@10：正确图片是否排在前面；
- MRR：第一张正确图片的位置；
- 零结果率；
- 搜索延迟；
- 单次搜索 API 成本；
- AI 标签接受率和驳回率。

模型、权重和 Prompt 的调整都通过同一套评测集比较，避免凭感觉修改。

## 12. 推荐实施顺序

### 第一阶段：统一语义和数据来源

- 建立六大体系、16 个图片标签、30 个文案卖点的权威目录；
- 建立别名、痛点、功能、结果、正反证据；
- 增加稳定 code；
- 区分人工标签、AI 建议和内容标签。

### 第二阶段：上传与 AI 审核

- 改造上传界面；
- 增加分析任务和状态；
- 拆分 Provider；
- 保存 OCR、视觉分析、AI 建议和分析版本；
- 支持接受和忽略 AI 建议。

### 第三阶段：本地混合搜索

- SQLite FTS5；
- 检索文档；
- Embedding；
- 标签、全文、向量三路召回；
- RRF 融合；
- 排除条件；
- 结果命中解释。

### 第四阶段：部署搜索基础设施

- PostgreSQL `tsvector`；
- pgvector；
- AI worker 容器；
- Provider 备用和超时策略；
- 重新索引命令。

### 第五阶段：精排和持续评测

- 接入 Reranker；
- 建立业务评测集；
- 调整权重与阈值；
- 记录搜索反馈和无结果查询；
- 定期回归。

## 13. 当前项目需要修正的方向

现有架构中的 `ModelProvider` 和 Skill 读取机制可以保留思想，但需要升级：

- 一个 Provider 拆成五类能力接口；
- AI 二级标签从名称文本改为标准标签外键；
- 保存人工、AI、审核状态和来源；
- 去掉强制 18–22 个内容标签；
- 搜索不再只做 SQL `LIKE`；
- 前端的“语义理解”展示必须连接真实查询计划；
- 相关推荐改为共享标签、语义和视觉特征的综合相关性；
- 所有分析和索引带版本，可重新生成。

这套方案不依赖某一家 API，也不要求项目团队发明新的机器学习算法。它使用成熟的全文检索、向量检索、排名融合和精排方法，并把六大体系的业务知识作为最重要的领域约束。
