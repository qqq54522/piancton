## 1. 项目回顾

### 1.1 这个项目要解决什么问题

卖点智库的核心目标不是“做一个能搜图片的图库”，而是做一个能理解业务卖点、能复用审核关系、能把素材准确交给业务人员的内部素材搜索系统。

在项目开始前，素材搜索主要存在几个问题：

| 问题 | 具体表现 | 对业务的影响 |
| --- | --- | --- |
| 搜索只看图片或标题 | 用户输入“背书”“孩子看得懂”“课后练一下”这类业务语言时，系统很难知道它对应哪个卖点 | 业务人员找图慢，容易漏素材 |
| 视觉相似不等于业务正确 | 像花瓣、普通图库或单纯向量检索，更多是找“看起来像”的图 | 可能返回画面相似但卖点不匹配的素材 |
| 模型直接搜索不稳定 | 大模型可以理解语义，但如果让模型直接决定结果，容易受提示词、上下文、模型状态影响 | 结果不可控，难解释，难验收 |
| 素材关系缺少审核闭环 | 图片是否真的支撑某个卖点，不能只靠 AI 判断 | 容易把“像是相关”的素材当成正式素材 |
| API 配置分散 | 如果每个功能各自填 Key、各自调用模型，后期很难维护 | 出问题时不知道是哪一个模型、哪一个 Key、哪一个任务失败 |
| 素材缺少稳定身份 | 图片名称、分组、版本、派生图都会变化 | 后期复盘、分享、精确定位都不稳定 |

所以本项目最终选择的方向是：

> 用业务知识组织素材，用 AI 理解搜索意图，用人工审核关系保证结果可信，用 API 调度中心统一管理模型调用，用身份码保证素材可以被稳定定位。

### 1.2 当前已经形成的完整业务流程

目前项目已经不是单点功能，而是一条完整链路：

```text
素材进入系统
→ AI 分析图片内容
→ AI 生成候选卖点话术
→ 负责人审核“主要表达 / 可以支持 / 不适用”
→ 审核通过的关系进入搜索金标准
→ 用户用自然语言搜索
→ 系统先判断是否为单张图片身份码
→ 如果不是精确查找，则进入 API 调度中心做意图理解
→ 匹配六大业务体系、核心卖点、证明点和素材专属话术
→ 按人工审核关系和素材匹配度排序
→ 返回可信素材、解释原因，并记录搜索日志
→ 后续通过日志继续评测和调优
```

### 1.3 为什么这个项目比普通搜索项目更复杂

普通图片搜索通常只需要解决“这张图像不像”“标题里有没有关键词”。卖点智库要解决的是“这张图能不能代表某个业务卖点，并且能不能被业务人员放心拿去用”。

因此它多了几层关键判断：

| 层级 | 作用 |
| --- | --- |
| 六大业务体系 | 先把业务地图固定下来，避免素材越积越乱 |
| 核心卖点 | 把业务人员真正要表达的卖点沉淀成可复用概念 |
| 证明点 / 表达点 | 说明一个卖点为什么成立、图片应该支撑什么 |
| 公共话术 | 让用户用口语、业务话、模糊话也能搜到正确方向 |
| 素材专属话术 | 让同一个卖点下面的不同图片可以被进一步区分 |
| 人工审核关系 | 决定素材能不能正式进入某个卖点搜索结果 |
| 身份码 | 保证某一张图、某一个版本可以被精确定位 |
| API 调度中心 | 保证模型调用可控、可追踪、可降级、可维护 |

这也是为什么本项目没有采用“直接把图片丢进向量库，然后搜相似图”的方案。

## 3. 实际效果

### 3.1 业务人员现在可以怎么用

当前系统支持业务人员直接用自然语言搜索，不需要先懂六大体系，也不需要手动选择“精准模式 / 智能模式”。

示例：

| 用户输入 | 系统理解方向 | 返回逻辑 |
| --- | --- | --- |
| “能体现我们这个背书的图” | 专家背书、专家合集、王玉龙专家等相关素材 | 优先返回已经通过关系确认、并且素材话术补强过的图片 |
| “孩子刚学完，想马上练几题确认一下” | 课后小测 | 匹配课后检测、即时练习、巩固反馈相关素材 |
| “有没有那种孩子一看就懂的动画课画面” | 动画精讲 | 匹配动画讲解、动态演示、降低理解门槛相关素材 |
| “想找适合拔高训练的图” | 专项培优 | 匹配培优、拔高、能力提升类素材 |
| “家长想知道孩子学得怎么样” | 学情报告反馈 | 匹配学习反馈、阶段报告、家长沟通类素材 |

这类搜索如果用传统图库，很容易只匹配到标题、颜色或画面元素；卖点智库会先理解业务意图，再回到审核通过的素材关系里找结果。

### 3.2 素材库 Agent 带来的效果

素材库 Agent 是本项目的一大亮点。它不是简单地“对图片聊天”，而是结合素材本身、业务体系、核心卖点、审核关系和素材话术，帮助业务人员理解一张图为什么可用、适合用在哪里、应该怎么讲。

它存在的原因是：业务素材真正被使用时，难点往往不是“有没有图”，而是“拿到这张图以后，能不能马上判断它适合哪个卖点、为什么适合、应该如何对外表达”。尤其是新同事、业务小白或临时来找素材的人，可能能搜到图片，但仍然不知道这张图该怎么讲，甚至会把图用到相邻但不准确的卖点上。

传统素材库通常只能做到：

- 展示图片；
- 展示文件名；
- 展示标签；
- 让用户自己判断能不能用。

素材库 Agent 做的是进一步解释：

| 能解释什么 | 具体价值 |
| --- | --- |
| 画面里有什么 | 帮用户快速理解图片内容，不用反复放大看细节 |
| 对应哪个业务卖点 | 把图片和“动画精讲、课后小测、专家背书”等卖点关联起来 |
| 为什么适合这个卖点 | 说明图片支撑卖点的理由，减少业务人员二次判断成本 |
| 适合什么使用场景 | 告诉用户这张图适合放在海报、详情页、朋友圈、课件还是汇报材料里 |
| 不适合怎么用 | 避免用户把图片用到错误卖点或错误场景中 |
| 可以怎么描述这张图 | 给业务人员生成可直接参考的素材讲解话术 |

它带来的变化是：

```text
以前：用户搜到图片后，还要自己判断“这张图到底能不能用”
现在：用户搜到图片后，可以让素材库 Agent 解释“为什么能用、怎么用、怎么讲”
```

这让卖点智库从“素材检索工具”进一步变成“素材理解助手”。它不仅提高找图效率，也提高了素材被正确使用的概率。

更具体地说，素材库 Agent 带来的结果包括：

| 结果 | 对业务的意义 |
| --- | --- |
| 降低新人使用门槛 | 不熟悉 16 个卖点的人，也能通过提问理解图片背后的业务表达 |
| 统一素材讲法 | 同一张图对销售、运营、设计和管理层都能形成更一致的解释 |
| 减少误用 | Agent 会基于已审核关系解释，不把未确认卖点说成正式事实 |
| 提升素材转化效率 | 搜到图后可以直接生成使用场景、推荐理由和对外讲法 |
| 反哺素材治理 | 常见追问可以暴露哪些图片缺少话术、关系或使用边界 |

因此，素材库 Agent 不是搜索之后附带的聊天框，而是本项目的“素材理解层”。搜索解决“找得准”，Agent 解决“讲得明白、用得正确”。

### 3.3 结果为什么更可信

本项目的搜索结果不是模型“猜出来”的，而是由三层机制共同保证：

| 机制 | 作用 |
| --- | --- |
| AI 意图理解 | 负责理解用户输入对应哪个体系、卖点、证明点 |
| 人工审核关系 | 负责判断某张图是否真的能代表或支撑这个卖点 |
| 素材专属话术与排序 | 负责在多个合格素材中选出更贴近当前搜索语句的素材 |

也就是说，AI 在这里主要负责“理解”和“推荐候选”，不是直接替业务负责人做最终判断。

素材库 Agent 也是同样逻辑：它可以解释素材，但解释依据必须来自图片内容、业务知识和审核关系，而不是脱离系统事实自由发挥。

### 3.4 身份码带来的效果

身份码解决的是“精确定位”的问题。

在素材系统里，图片标题可能会改，分组可能会调整，版本可能会替换，衍生尺寸可能会追加。如果没有稳定身份，后续会出现这些问题：

| 没有身份码时 | 有身份码后 |
| --- | --- |
| 只能凭文件名或截图找图 | 可以通过当前图片唯一身份码精确定位 |
| 同组横版、竖版容易指错 | 每张物理图片各有一个身份码 |
| 删除后列表仍残留历史 | 删除即清空编码并从台账消失 |
| 搜索要依赖语义判断 | 精确码查询不进入语义搜索，结果更快更稳 |

所以系统搜索时会先判断用户输入是否是图片身份码。只要命中当前活动图片，就直接返回对应素材，不走模型理解链路。

### 3.5 API 调度中心带来的效果

API 调度中心解决的是“模型调用不可控”的问题。

如果每个功能都自己配置 API Key，会出现：

- 哪个 Key 正在用不清楚；
- 哪个模型支持图片不清楚；
- 某次失败是额度问题、网络问题、格式问题还是模型能力问题不清楚；
- 想换模型时要改多个地方；
- 前端和日志里容易暴露敏感 Key。

现在的 API 调度中心把这些能力集中起来：

| 能力 | 作用 |
| --- | --- |
| API 库存 | 集中管理不同供应商、模型和 Key |
| Key 指纹 | 只展示脱敏标识，不暴露完整密钥 |
| 能力识别 | 区分 text_json、vision_json 等能力 |
| 任务槽位 | 不同任务可以绑定不同模型和调用策略 |
| 健康检查 | 判断 API 是否可用 |
| 调用追踪 | 记录每次调用的模型、耗时、状态和错误 |
| 错误码体系 | 把失败原因结构化，便于排查 |
| 降级策略 | 模型不可用时尽量走缓存、数据库或备用路径 |

因此，API 调度中心不是“多做了一个配置页”，而是整个 AI 搜索系统的运行控制台。

### 3.6 卖点话术带来的效果

卖点话术解决的是“用户不会按标准名搜索”的问题。

业务人员通常不会输入非常规范的卖点名称。例如他们可能不会直接搜“动画精讲”，而是搜：

- “孩子一看就懂的图”
- “动画讲知识点”
- “把复杂知识讲简单一点”
- “适合做课程亮点的动态图”

如果系统只存标准卖点名，就很难覆盖这些真实表达。

所以本项目把话术拆成两类：

| 话术类型 | 作用 |
| --- | --- |
| 公共话术 | 帮系统理解用户大概在找哪个卖点 |
| 素材专属话术 | 帮系统在同一卖点下区分不同图片 |

这样做的好处是：

1. 用户可以用自己的话搜索，不需要背标准术语。
2. 同一个卖点下的素材不会混在一起，排序更细。
3. 后续搜索日志可以反过来补充话术，让系统越用越准。
4. 话术经过治理后进入系统，避免无边界扩词导致误召回。

## 4. 问题与复盘

### 4.1 为什么没有采用传统图库式搜索

传统图库式搜索适合找“画面元素”，不适合找“业务卖点”。

例如用户搜索“背书”，传统图库可能会找：

- 有人物的图片；
- 有老师的图片；
- 有证书感的图片；
- 画面风格相似的图片。

但业务真正要的是：

- 这张图是否表达专家背书；
- 是否能证明课程可信；
- 是否经过负责人确认；
- 是否适合当前业务场景。

视觉相似并不能证明业务正确。因此本项目最终没有把“相似图片搜索”作为主链路，而是采用：

```text
业务意图理解
→ 卖点 / 证明点识别
→ 人工确认关系约束
→ 素材专属话术排序
→ 返回结果并解释原因
```

### 4.2 为什么不能让模型直接决定结果

模型可以帮助理解，但不能作为最终事实来源。

项目测试过程中也验证了这一点：不同模型在相同任务下的稳定性、耗时和空结果表现不同。如果完全依赖模型直接返回素材，会出现：

- 同一句话多次搜索结果不一致；
- 模型解释听起来合理，但素材关系未必真实成立；
- 模型调用失败时，搜索功能整体不可用；
- 搜索质量难以复盘，因为缺少结构化依据。

因此最终设计中，模型只负责意图理解和候选辅助，真正决定素材是否可用的是人工审核关系和数据库中的业务事实。

### 4.3 为什么必须有人工作业关系

AI 可以看懂图片大概内容，但“这张图能不能作为某个卖点的正式素材”是业务判断。

例如一张图里有老师，不代表它一定能表达“真人老师督学”；一张图里有报告，也不代表它一定能表达“学情报告反馈”。是否能代表这个卖点，需要业务负责人确认。

所以系统设置了三类关系：

| 关系 | 含义 |
| --- | --- |
| 主要表达 | 这张图最核心表达的就是这个卖点 |
| 可以支持 | 这张图可以作为这个卖点的辅助素材 |
| 不适用 | 这张图不应该进入该卖点搜索结果 |

这个设计让搜索结果有了“金标准”，也让后续评测有了依据。

### 4.4 为什么要做 API 调度中心

API 调度中心是项目中非常关键的一步，因为 AI 功能越多，模型调用就越不能散落在代码和环境变量里。

如果没有调度中心，后续会很难回答：

- 现在图片分析用的是哪个模型？
- 搜索意图理解用的是哪个模型？
- 哪个 Key 失效了？
- 哪个任务最近失败率高？
- 哪个模型支持图片输入？
- 为什么这次搜索耗时特别长？

API 调度中心把这些问题变成可配置、可查看、可追踪的系统能力。它让项目从“能跑”变成“能长期维护”。

### 4.5 为什么要做身份码

身份码不是为了好看，而是为了解决素材资产的长期可追溯。

素材系统会持续变化：

- 图片会替换；
- 文件名会修改；
- 分组会调整；
- 衍生尺寸会追加。

如果没有图片身份码，后期很难确认“用户说的是哪一张图”。当前活动图片的唯一身份码提供确定性入口：输入码就不需要 AI 猜测，直接定位图片；删除后该码随图片一起消失，恢复时重新生成。

### 4.6 当前仍然需要注意的问题

| 问题 | 当前处理方式 | 后续注意 |
| --- | --- | --- |
| 话术可能过宽 | 通过人工治理和拒绝泛化词控制 | 继续根据搜索日志清理误召回词 |
| 模型调用可能不稳定 | API 中心记录健康、错误码和调用链路 | 继续补充压力测试和降级策略 |
| Agent 解释可能偏离事实 | 解释时绑定图片内容、审核关系和业务知识 | 避免 Agent 脱离素材事实自由发挥 |
| 部分卖点素材不足 | 空结果时不强行返回不可靠素材 | 后续通过业务补图或补关系解决 |
| 查询表达会持续变化 | 用搜索日志收集真实输入 | 定期把高频搜索转成公共话术 |
| 业务体系会迭代 | 体系稳定，概念和关系可版本化 | 新增体系或卖点时必须有迁移和验收 |

## 5. 后续规划

### 5.1 继续补全卖点话术

目前已经完成了部分重点卖点的话术深化，后续可以继续覆盖剩余卖点，让 16 个核心卖点都具备更充分的真实搜索表达。

重点不是无限扩词，而是把业务人员真实会输入的表达沉淀下来。

### 5.2 继续用真实搜索日志调优

后续应定期复盘搜索日志，重点看：

- 哪些词搜到了正确素材；
- 哪些词返回为空；
- 哪些词召回了不该出现的素材；
- 哪些搜索说明需要补公共话术；
- 哪些搜索说明需要补素材专属话术；
- 哪些素材需要补充 Agent 解释依据；
- 哪些搜索说明当前素材库本身缺图。

搜索日志会成为后续优化系统的主要依据。

### 5.3 增强 API 调度中心的生产级能力

后续 API 调度中心可以继续加强：

- 更多模型供应商接入；
- 多 Key 自动轮换；
- 更细的任务级预算；
- 更完整的失败重试策略；
- 更清晰的调用耗时看板；
- 更严格的生产环境密钥管理。

这部分会决定系统未来能不能支持更高并发、更大素材量和更多 AI 任务。

### 5.4 补充生产环境运维材料

后续正式交接时，建议继续补齐：

- 生产部署说明；
- 数据库备份和恢复说明；
- API Key 轮换说明；
- 管理员日常维护 SOP；
- 新素材入库 SOP；
- 新卖点新增 SOP；
- 素材库 Agent 使用 SOP；
- 搜索质量验收表。

这些内容不是为了写文档而写文档，而是为了让系统离开开发者后仍然能被稳定使用。

### 5.5 持续完善新人复刻文档

项目已经提供了新人复刻指南，后续可以继续把真实截图补进去，形成更完整的“无痛复刻版”：

- 从 GitHub 仓库拉代码；
- 配置 `.env` 示例；
- 启动 Docker 或本地开发环境；
- 初始化数据库；
- 创建管理员账号；
- 填写 API 示例配置；
- 上传第一张素材；
- 执行 AI 分析；
- 审核卖点关系；
- 用搜索框验证结果；
- 查看 API 调用日志；
- 处理常见报错。

需要强调的是，真实 API Key 不能写进文档。文档中只放示例格式，例如：

```text
OPENAI_API_KEY=sk-xxxxxx
GEMINI_API_KEY=AIza-xxxxxx
```

具体 Key 由复刻者自己在本地或服务器环境中填写。

## 6. 结项判断

从工程阶段看，本项目已经完成核心闭环：

```text
素材管理
→ 业务知识沉淀
→ AI 图片分析
→ 卖点话术生成
→ 人工审核关系
→ 单框自然语言搜索
→ 素材库 Agent 解释
→ 身份码精确定位
→ API 调度中心治理
→ 搜索日志与评测调优
```

它已经不是一个简单的“图片搜索 Demo”，而是一个围绕业务卖点组织素材、审核素材、检索素材和持续优化素材质量的内部知识系统。

本项目可以结项的原因是：

1. 核心业务流程已经跑通。
2. 关键数据结构已经建立。
3. 搜索主链路已经形成。
4. 素材库 Agent 已经补上“素材为什么能用、怎么用”的解释能力。
5. API 调度中心已经接管模型调用。
6. 身份码、审核关系和日志机制已经为长期维护打好基础。
7. 已经具备新人复刻、后续扩展和持续调优的文档基础。

后续工作不再是“把项目从无做到有”，而是进入生产运营阶段：继续补充素材、补充话术、复盘搜索日志、优化模型调度，并根据真实业务使用情况持续迭代。

## 7. 汇报时可以直接使用的一句话总结

卖点智库最终交付的不是一个普通图库，而是一套“业务卖点驱动的素材搜索与解释系统”：它用 AI 理解用户想找什么，用人工审核关系保证素材是否可信，用素材库 Agent 解释图片为什么能用、怎么用、怎么讲，用身份码保证素材可追溯，用 API 调度中心保证模型调用可维护，最终让业务人员可以用一句自然语言快速找到并理解能支撑对应卖点的素材。
