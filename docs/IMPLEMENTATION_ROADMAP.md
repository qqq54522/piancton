# Piancton 标签、AI 与搜索改造实施规划

状态：分阶段实施中；真实数据尚未正式迁移，搜索尚未切换

## 0. 当前落地进展

截至 2026-06-24，已完成第一轮非破坏性改造：

- 新增 `taxonomy/catalog.json`，六大体系、16 个图片业务标签和 30 个文案卖点映射由同一份机器可读目录维护。
- 标准标签已具备 `code`、`node_type`、`assignable`、`status`、`taxonomy_version` 和 `sort_order`。
- 上传时支持记录设计师人工主业务标签与附加标签；AI 建议保存为独立来源，不覆盖人工主标签。
- 新增 `analysis_runs` 与 `image_business_labels`，AI 分析批次、标签来源、审核状态和证据可追溯。
- 详情页支持接受/拒绝 AI 业务标签建议；被拒绝的 AI 建议不进入搜索命中和索引文档。
- 新增数据库默认搜索 + Meilisearch 可选搜索的降级层；Meilisearch 不可用时自动回退数据库模糊搜索。
- 新增 `scripts.rebuild_search_index` 与搜索文档生成逻辑，索引可由主数据库重建。
- 上传、改标题、改标签、删除、恢复、永久删除和 AI 分析完成后，会尽力增量同步搜索索引；同步失败不阻断主流程。
- `scripts.seed_taxonomy` 会在迁移后把已有 `image_tags` 回填为人工业务标签，确保旧图片也有设计师主归属。
- Meilisearch 容器已作为 Docker Compose 的可选 `search` profile，不会影响默认基础服务启动。

已验证：

- 后端 `pytest`、Ruff、Pyright 通过。
- 前端 ESLint、TypeScript、Vitest、生产构建通过。
- 使用旧库副本完成 Alembic 迁移预演、六大体系 seed、人工业务标签回填和搜索文档 dry-run。

尚未执行：

- 未迁移真实 `data/piancton.db`。
- 未把线上/本地业务搜索正式切到 Meilisearch。
- 未启动实际 Meilisearch 服务验证真实索引写入与搜索结果排序。

## 1. 先给结论

这次改造整体属于“中等难度”，不是简单换一个搜索接口，也不需要自研机器学习算法。

真正的工作量主要来自：

1. 把六大体系从普通标签整理成稳定、可扩展的业务目录；
2. 区分人工标签、AI 建议和图片内容标签；
3. 让上传后的 AI 分析可以审核和追溯；
4. 引入可降级的混合搜索；
5. 保证本地 SQLite 与线上 PostgreSQL 使用同一套业务逻辑。

不建议一次性全部重写。项目应分阶段上线，每个阶段都可以独立验收和回滚。

## 2. 第一版最小依赖

第一版不要求同时寻找五种模型 API。

唯一必需的外部 AI 能力是：

> 一个可以接收图片、理解中文并稳定返回 JSON 的多模态大模型 API。

它在第一版同时负责：

- 看懂图片内容；
- 读取图片中主要文字；
- 根据六大体系推荐业务标签；
- 生成图片摘要和隐性内容标签；
- 理解复杂的业务搜索句子。

因此，第一版不单独要求：

- 专用 OCR API；
- Embedding API；
- Reranker API；
- 独立的图片向量模型。

这些能力以后找到合适 API 再接入，不影响第一版数据结构和界面。

### 2.1 能力优先，不绑定厂商名称

项目配置的是能力，而不是写死厂商：

```text
支持图片输入
支持中文
支持 JSON 输出
支持文本输入
```

任何第三方中转 API，只要兼容项目适配器并满足这些能力，就可以使用。

如果某个 API 只有文本能力：

- 可以用于搜索理解；
- 不能用于图片分析；
- 系统应在管理页面明确显示能力缺失，而不是分析失败后才发现。

### 2.2 后续增强

| 增强能力 | 作用 | 是否第一版必需 |
|---|---|---:|
| 专用 OCR | 提升小字、密集文字识别 | 否 |
| Embedding | 提升不同措辞之间的语义召回 | 否 |
| Reranker | 提升前几十张候选的最终排序 | 否 |
| 图片向量 | 支持以图搜图和视觉相似搜索 | 否 |

没有这些增强时，第一版仍可以依靠：

- 六大体系概念词典；
- 大模型查询扩展；
- Meilisearch 中文全文、前缀和错字搜索；
- 人工与 AI 标签权重；
- 结构化过滤。

## 3. 部署难度

### 3.1 当前部署

当前线上结构是：

```text
Nginx + FastAPI + PostgreSQL
```

### 3.2 改造后的目标结构

第一阶段搜索上线后：

```text
Nginx
  -> FastAPI
       -> PostgreSQL
       -> Meilisearch
       -> 第三方多模态模型 API
```

稳定运行后再增加：

```text
AI Worker
  -> 处理上传后的分析和索引任务
```

部署增加的主要内容只有：

- 一个 Meilisearch 容器；
- 一个持久化搜索索引 volume；
- 一组搜索服务环境变量；
- 后续可选的 worker 容器。

不需要搭建 Elasticsearch 集群，也不需要 GPU 服务器。

### 3.3 难度评价

| 部分 | 难度 | 说明 |
|---|---:|---|
| 六大体系目录重构 | 中 | 涉及数据迁移，但不增加服务 |
| 多模态 API 接入 | 中 | 当前已有 Provider 基础，需要补能力检测和版本记录 |
| 上传审核界面 | 中 | 需要调整前后端数据结构 |
| Meilisearch 本地运行 | 低到中 | 单进程、固定版本、健康检查 |
| Meilisearch 线上部署 | 中 | Docker Compose 增加一个内部服务 |
| Embedding / Reranker | 中 | 可选，找到 API 后再接 |
| 标签版本管理后台 | 中到高 | 建议后置，不阻塞第一版 |

粗略上，这不是一两次小修改，而是适合拆成数个可验收迭代的改造。最大风险不是部署，而是标签数据边界没有先固定就开始改搜索。

## 4. 标签树必须支持未来扩展

### 4.1 不再写死“一级、二级”

当前代码使用 `is_secondary`，这会把系统限制在固定两级。

目标结构只保留：

- `code`：稳定业务编码；
- `parent_code`：父节点编码；
- `name`：展示名称；
- `node_type`：体系、业务概念或导航节点；
- `assignable`：图片能否直接关联；
- `status`：草稿、启用、停用；
- `aliases`：同义词；
- `positive_evidence`：正向判断依据；
- `negative_evidence`：排除依据；
- `sort_order`。

层级深度通过父子关系计算，不在业务代码中写死。

### 4.2 `assignable` 必须独立于“是否叶子”

这是未来新增三级标签时最关键的设计。

如果仍规定“只有最末级标签可以选择”，那么在一个已有二级标签下新增三级标签后：

- 原二级标签突然变成非叶子；
- 原有图片关联可能变成非法；
- 上传和搜索逻辑都会变化。

因此改为显式 `assignable`：

```text
同步自学体系                 assignable=false
└── AI拍题精学               assignable=true
    ├── 拍题分步讲解         assignable=true
    └── 拍题相似题推荐       assignable=true
```

即使增加三级标签，原“AI拍题精学”仍然可以继续关联图片。是否逐步迁移到更细标签，由业务决定，而不是由树结构强迫。

### 4.3 父级搜索自动包含后代

搜索索引为每个标签保存：

```json
{
  "code": "photo_guided_explanation",
  "ancestorCodes": [
    "sync_self_study",
    "photo_learn"
  ]
}
```

这样：

- 搜索“同步自学体系”可包含其所有后代；
- 搜索“AI拍题精学”可包含直接关联和三级子标签图片；
- 新增层级不需要重写搜索 SQL 或 Prompt。

### 4.4 AI 只返回稳定 code

模型不能返回自由文本标签名称，而应从动态目录中选择：

```json
{
  "label_code": "photo_learn"
}
```

新增标签后：

1. 在目录中增加一个节点；
2. 发布新目录版本；
3. Prompt 自动加载新目录；
4. 搜索索引重建或增量更新；
5. 可选重新分析历史图片。

正常情况下不需要修改：

- Pydantic schema；
- API 路由；
- 搜索算法；
- 前端标签树组件；
- Provider 代码。

### 4.5 标签不能直接删除

已有图片使用的标准标签只能：

- 改名；
- 增加别名；
- 移动父级；
- 标记停用；
- 映射到替代标签。

不能因为删除一个标签而把图片放入回收站。当前 `TagService.delete()` 的行为必须在改造阶段修正。

## 5. 权威目录与版本

### 5.1 第一版目录

仓库新增一份机器可读目录，例如：

```text
taxonomy/catalog.yaml
```

它包含：

- 六大体系；
- 当前 16 个图片业务标签；
- 30 个文案卖点映射；
- 别名；
- 痛点表达；
- 功能表达；
- 结果表达；
- 正向证据；
- 排除证据；
- 父子关系；
- 是否可直接打标。

Python 校验、数据库同步、AI Prompt 和搜索索引都从这份目录读取。

### 5.2 目录版本

每次发布目录变化必须生成版本：

```text
2026.06.1
2026.06.2
```

版本记录：

- 新增了哪些节点；
- 改名了哪些节点；
- 哪些节点停用；
- 父子关系变化；
- 别名和证据规则变化；
- 是否需要重新分析或只需重新索引。

### 5.3 未来管理界面

第一版可以通过目录文件修改，确保规则先稳定。

后续再增加“标签目录管理”页面：

1. 创建草稿版本；
2. 新增或调整节点；
3. 查看受影响图片；
4. 校验 code、循环和重名；
5. 发布版本；
6. 自动触发重新索引。

管理页面最终也是修改同一套目录数据，不会产生另一套规则。

## 6. 图片标签数据模型

目标是使用一张统一关系表表达人工与 AI 判断：

```text
image_business_labels
```

建议字段：

| 字段 | 作用 |
|---|---|
| image_id | 图片 |
| label_code | 稳定标签 code |
| origin | `manual` / `ai` |
| role | `primary` / `secondary` |
| review_status | `accepted` / `pending` / `rejected` |
| confidence | AI 置信度 |
| evidence_level | A / B / C |
| reason | 判断依据 |
| analysis_run_id | 来自哪次 AI 分析 |
| created_by | 人工操作者 |

约束：

- 每张图片最多一个人工主标签；
- 人工主标签不会被 AI 覆盖；
- AI 可以推荐跨体系标签；
- 接受或拒绝 AI 建议都保留记录；
- 被拒绝标签不会在下一次相同规则分析中反复提示，除非模型或目录版本改变。

## 7. 上传界面规划

### 7.1 第一屏：上传与人工归属

- 图片选择和预览；
- 人工主标签，必选；
- 人工附加标签，可选；
- 标题可选；
- “上传并 AI 分析”；
- “仅上传”。

批量上传时可以选择：

- 全部图片使用同一主标签；
- 为单张图片单独调整。

### 7.2 第二屏：分析状态

- 等待；
- 正在理解图片；
- 正在建立搜索信息；
- 已完成；
- 失败，可重试。

第一版不单独显示“OCR 中”，因为图片文字读取由同一个多模态模型完成。

### 7.3 图片详情：AI 建议审核

显示：

- 人工主标签；
- 人工附加标签；
- AI 推荐标签及置信度；
- 跨体系提示；
- 推荐原因；
- 接受、拒绝；
- 图片摘要；
- 图片中文字；
- 人物、场景、动作、颜色、风格等隐性标签；
- 当前索引状态。

## 8. 搜索第一版与增强版

### 8.1 第一版

```text
用户查询
  -> 标准标签、别名和业务表达直接匹配
  -> 复杂句子调用同一个大模型生成查询计划
  -> Meilisearch 中文全文、前缀、错字和过滤搜索
  -> 人工主标签与已确认标签加权
  -> 返回命中原因
```

第一版即使没有 Embedding，也能解决大量“不使用标准标签名称”的搜索。

### 8.2 增强版

找到稳定 Embedding API 后：

```text
关键词搜索 + 向量搜索 -> 混合排序
```

找到稳定 Reranker API 后：

```text
Top 30 或 Top 50 -> 精排
```

这些增强只改变搜索 Provider 和索引配置，不改变图片标签数据模型。

## 9. 分阶段实施

### P0：冻结与备份

目标：任何改造都可撤回。

- 备份 SQLite、图片目录和配置；
- 导出当前标签树和图片关联；
- 为当前规则记录基线版本；
- 暂停随意删除六大体系节点。

风险：低。  
对现有用户影响：无。

### P1：权威目录与任意层级

目标：解决未来新增二级、三级标签需要改代码的问题。

- 创建 `taxonomy/catalog.yaml`；
- 为 6 + 16 + 30 个概念分配稳定 code；
- 增加别名、证据和映射；
- 数据库为标准标签增加 code、类型、assignable、状态；
- seed 改为按 code 同步；
- Prompt 动态读取目录；
- 增加目录一致性测试；
- 保护六大体系，禁止直接删除。

风险：中。  
回滚：保留原字段和旧读取路径。

### P2：人工与 AI 标签来源

目标：正确表达“设计师主标签 + AI 跨体系建议”。

- 新增统一图片业务标签关系；
- 新增分析批次和规则版本；
- 迁移现有人工与 AI 文本标签；
- 改造图片详情审核；
- 去掉强制 18–22 个隐性标签；
- 标题改为可选，不参与高权重检索。

风险：中。  
回滚：旧表暂时只读保留，验证后再清理。

### P3：搜索引擎影子接入

目标：引入 Meilisearch，但不立即替换线上结果。

- 增加 SearchProvider 接口；
- 增加 Meilisearch 客户端；
- 建立搜索文档；
- 增加 outbox 和全量重建命令；
- 本地与 Docker Compose 使用固定版本；
- 新旧搜索同时运行并记录差异；
- 页面仍使用旧搜索。

风险：低到中，因为主数据库不变。  
回滚：关闭功能开关。

### P4：切换业务搜索

目标：业务人员开始使用新搜索。

- 启用中文全文、别名、查询计划和过滤；
- 展示命中原因；
- 复杂查询调用大模型；
- 模型失败时自动降级；
- 记录零结果查询和用户点击。

风险：中。  
回滚：`SEARCH_BACKEND=database`。

### P5：可选语义增强

目标：提升长句和不同措辞搜索。

- 接入 Embedding；
- 重建向量索引；
- 调整混合比例；
- 可选接入 Reranker；
- 使用评测集比较效果。

风险：中。  
这不是第一版上线前置条件。

## 10. 功能开关与回滚

建议增加：

```env
SEARCH_BACKEND=database
AI_ANALYSIS_ENABLED=true
AI_ANALYSIS_MODE=sync
SEMANTIC_SEARCH_ENABLED=false
RERANK_ENABLED=false
```

上线顺序：

1. 数据结构先上线；
2. 新索引后台构建；
3. 影子搜索验证；
4. 小范围用户切换；
5. 全量切换。

出现问题时：

- 搜索切回数据库；
- 关闭语义和精排；
- 保留人工标签与图片；
- Meilisearch 索引可删除后重建；
- 不回滚已经安全写入的主数据。

## 11. 验收标准

### 标签

- 新增三级标签不修改业务代码；
- 原二级标签图片仍然有效；
- 父级搜索能召回后代图片；
- AI 只能返回有效 code；
- 停用标签不会删除图片。

### 上传

- 无标题图片可以上传和分析；
- 人工主标签不被 AI 覆盖；
- AI 可以提出跨体系建议；
- 建议可接受或拒绝；
- 模型故障不影响图片保存。

### 搜索

- 标准标签、别名和口语表达能召回；
- 错别字和前缀有合理结果；
- 长句可生成可解释的查询计划；
- 模型或搜索服务故障时有降级；
- 删除或回收站图片不会出现在最终结果。

### 部署

- 本地和线上使用相同 SearchProvider；
- Meilisearch 不暴露公网；
- API Key 只在后端；
- 索引可从主数据库全量重建；
- 重启容器后索引仍存在。

## 12. 当前明确不做

- 不一次性寻找并绑定多个模型厂商；
- 不把专用 OCR 作为前置依赖；
- 不同时部署 Meilisearch、Qdrant 和 pgvector；
- 不直接修改 Meilisearch 源代码；
- 不让 AI 自动覆盖人工标签；
- 不再用 `is_secondary` 判断标签层级；
- 不在没有评测数据时凭感觉频繁调权重。

## 13. 下一步

P0–P3 已完成第一轮非破坏性实现，并已通过旧库副本迁移预演。当前下一步是：

1. 解决 Docker Hub 拉取超时问题，可使用 Docker Desktop 全局 registry mirror，或在 `.env` 中覆盖基础镜像完整名称；
2. 启动 `docker compose --profile search up --build -d`；
3. 执行 `python -m scripts.rebuild_search_index`，验证真实 Meilisearch 索引写入；
4. 用同一批查询比较 `SEARCH_BACKEND=database` 与 `SEARCH_BACKEND=meilisearch` 的结果、命中原因和降级行为；
5. 只有真实搜索实例验证通过后，再迁移真实 `data/piancton.db`；
6. 只有迁移后的真实库和搜索索引都验证通过后，再把业务搜索切到 Meilisearch。
