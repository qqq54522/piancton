### 0.6 Phase 4 本轮交接记录（2026-07-15）

#### 完成内容

- `SearchService` 缩为同步脚本/异步 API 的薄门面和依赖装配入口，在线流水线移入 `AsyncSearchOrchestrator`。
- 外部分支的启动、缓存和主会话水合独立到 `SearchExternalBranches`，总截止内的唯一一次重排独立到 `SearchRerankCoordinator`；总编排器由 455 行收口到 256 行，避免一个位置同时承担所有异步细节。
- FastAPI 搜索端点改为 `async def`，调用 `await search_async(...)`；旧脚本和同步测试继续使用兼容 `search(...)`。
- Meilisearch 和 Embedding 外部分支先返回轻量候选 ID/向量，ORM 图片由请求主会话顺序装载；并发线程不共享 SQLAlchemy Session。

- 生成式图片摘要裁判退出默认在线链路；Reranker 失败或超时时直接使用本地融合分数。
- 新增查询理解与 Embedding 查询向量 TTL/LRU 缓存，不缓存 ORM 实体和最终搜索结果。

### 0.8 Phase 6 本轮清理边界（2026-07-15）

#### 删除的旧职责

- `image_tags`：不再把固定标签直接挂到图片；六大体系通过业务概念的多对多关系影响筛选和排序。
- `image_categories`：删除旧精准筛选使用的 `scene/function` 图片分类。
- `image_level2_categories`：删除旧 AI 二级分类持久化；客观画面进入 Semantic Profile V2 和 `content_tags`，业务判断进入 `asset_concept_links`。
- `image_business_labels`：删除以固定 `Tag` 为中心的人工/AI 图片业务标签；人工与 AI 来源、审核状态、关系角色由 `asset_concept_links` 承担。
- `search_logs.requested_mode` 及 `precise/smart/configured` 请求分支：普通业务端和后端统一执行同一条可降级搜索编排。

#### 保留的新职责

- 被负责人拒绝的 AI 话术同时从 Semantic Profile 的搜索表达投影中排除，不再继续影响模糊召回、Embedding 或重排；客观内容标签继续保持辅助信号，不能压过人工确认业务语言。
- 人工新增、AI 话术审核和卖点关系确认后会按主图刷新 Meilisearch 派生文档和 Embedding；数据库仍是事实来源，外部索引同步失败不阻断人工操作。

### 0.24 素材独有话术删除闭环（已完成，2026-07-16）

- “当前素材独有话术”的每条已确认项右侧提供常驻删除按钮，不依赖悬停，不再出现只能新增和采纳、不能移除的单向维护流程。
- 删除采用可恢复的软删除：将人工新增或已采纳 AI 话术标记为 `rejected`，立即从当前清单、数据库直接召回、Meilisearch、Embedding 和重排语义投影退出，但保留来源和审核轨迹。
- 删除后重新添加相同的人工话术会恢复原记录为 `accepted`，避免重复记录并保留连续审计历史。
- 删除和恢复均同步刷新素材组主图派生索引；无数据库结构迁移，不修改素材业务关系、公共话术或图片版本。

### 0.25 素材详情 AI 信息收口（已完成，2026-07-16）

- 素材详情的 AI 分析区只展示“画面事实”“场景”“素材独有搜索表达”三组高价值信息，并保留独立的语义总结。
- OCR、主体、动作、视觉风格、画面可见产品功能、画面排除边界和客观内容标签不再铺在设计师详情页，避免重复信息和低价值标签把页面拉长。
- 本轮只调整展示层，不删除 Semantic Profile V2 或 `content_tags` 数据；隐藏字段继续作为 OCR、关键词、Embedding 和 Reranker 的后台搜索辅助，避免因界面精简降低召回能力。
- 无接口、数据库结构或真实素材数据迁移；新增展示分组测试和文档一致性约束，防止无关标签重新回流详情页。

### 0.2 已由用户明确确认的事实

1. 六大体系已经确定，名称和大方向不会改变：
   - 同步校内体系
   - 同步考点体系
   - 同步培养体系
   - 同步规划体系
   - 同步自学体系
   - 同步伴学体系
2. 六大体系下面的证明点、功能模块和细分结构仍可能调整、合并或拆分，不能写死成固定数据库树。
3. 一张图片可能同时证明多个业务概念，也可能为多个体系提供支撑。
4. 上传到正式图片库的图片，已经经过业务负责人审核。负责人审核属于发布准入，不需要再用“业务评分”判断图片质量。
5. 普通业务人员是否最终使用图片，是他们的选择；点击、下载和“不相关”反馈只用于优化搜索排序，不反向否定图片审批结论。
6. 延展尺寸不是首次上传的必填项。主图可以先独立发布，延展图做好后再随时追加。
7. 六大体系是稳定业务地图和搜索信号，但不能成为所有搜索的唯一硬过滤条件。
8. 业务人员的搜索通常仍会围绕六大体系、产品能力、痛点和结果表达，但可能非常口语化、不完整或表述离谱。
9. 项目现有的模型、Embedding、Reranker、Meilisearch 等能力应当合理利用，但不能为了“都用上”而串行堆叠在每次在线搜索中。
10. 在线搜索必须有明确的总时间预算、超时和降级路径，任何单一模型接口不可用都不能导致搜索完全失效。
11. 业务负责人将对每张正式图片可证明的业务点进行确认；这份确认结果是图片业务关系的首要真值来源。原始设计任务和原文件名不是必填业务材料。
12. 三四十张正式图片是完整验收和最终调优规模，不是开始改造的门槛。Phase 0 可以先用 3-6 张代表图片和对应查询启动，后续持续追加。

### 0.3 本方案的核心结论

系统不再以“单张图片 + 固定二级标签”为中心，而改为：

```text
稳定六大体系
    ↕ 多对多
可版本化业务概念
    ↕ 多对多
图片素材组
    ↕ 可选、可延后
主图 / 延展尺寸 / 备选版本 / 历史版本
```

搜索语言主要挂在“业务概念”上；图片只保存自身独有的画面语义、文字、风格、使用场景和与业务概念的关系。这样更换图片或新增尺寸时，不需要重复建立整套搜索语言。

### 0.4 后续工作不得擅自改变的原则

- 不得把下层业务内容重新固化为只能单选的二级标签树。
- 不得要求首次上传时必须同时上传延展尺寸。
- 不得要求每张图片必须强行选择一个六大体系主标签才能上传。
- 不得把“负责人审批”和“用户使用反馈”混为一套评分。
- 不得要求业务用户自己选择“精准搜索/智能搜索”。
- 不得让生成式大模型成为搜索可用性的单点依赖。
- 不得在没有更新本文档决策记录的情况下改变核心数据模型或搜索链路。

## 3. 项目目标与非目标

### 3.1 项目目标

1. 业务人员用标准词、简称、痛点、结果、场景或口语表达，都能在可控时间内找到最相关的正式图片。
2. 六大体系保持稳定，但下层业务结构可以增删、改名、合并、拆分和跨体系复用。
3. 一张图片可以主要表达一个概念，同时支撑多个其他概念。
4. 更换主图时可以继承已确认的业务关系和搜索语言，避免从零打标。
5. 延展尺寸可以以后随时追加，不增加首次上传阻力。
6. 搜索返回素材组，避免同一画面的横图、竖图和方图重复占据结果页。
7. 上传阶段充分使用 AI，在线搜索阶段控制模型调用数量和总延迟。
8. 通过真实查询评测和单结果反馈逐步改善搜索，而不是不断人工堆标签。

### 3.2 非目标

- 不承诺对任意毫无业务含义的输入都能返回唯一正确图片。
- 不用系统重新评价已经由业务负责人审核通过的图片质量。
- 不在第一阶段建设复杂的通用数字资产管理平台。
- 不在第一阶段替换现有登录、权限、存储、缩略图、下载和审计基础设施。
- 不追求把所有模型接口都放进在线必经链路。
- 不在证明点尚未稳定时强行完成永久性分类定稿。

## 4. 核心产品原则

### 4.1 六大体系是业务地图，不是唯一搜索闸门

六大体系用于：

- 导航和筛选。
- 帮助理解用户搜索的业务方向。
- 提升相关概念和图片的排序。
- 给管理端观察素材覆盖情况。

只有用户明确选择某个体系筛选器时，体系才是硬过滤。普通自然语言搜索中，体系默认只作为排序信号。

### 4.2 业务概念是可变化的中间层

“业务概念”统一承载目前资料中的功能、痛点、结果、场景、服务能力、教学方法和品牌证据主题。它不要求永久稳定，也不要求只能属于一个体系。

建议的初始概念类型：

- `product_function`：产品功能，如 AI 错题本、AI 私教。
- `course_module`：课程/训练模块，如专项突破、考前突击。
- `teaching_method`：教学方法，如苏格拉底式提问、底层逻辑、动画可视化。
- `user_pain`：用户痛点，如只抄答案、家长不会辅导、叫不动管不住。
- `desired_outcome`：期望结果，如五到八分钟讲懂、举一反三、家长省心。
- `service_capability`：服务能力，如真人督学、学习规划、定期反馈。
- `brand_evidence`：品牌/师资/数据/学校实证主题。
- `business_term`：现阶段仍需要保留但尚未完成结构化的业务说法。

类型字段采用可扩展字符串，不应写死为不可迁移的数据库枚举。

### 4.3 “证明点”是关系，不是必须固定的树节点

当一张专家讲座图片能证明“师资背书”，同时支撑“新中考教研”“专家规划”和“重难点培优”时，正确表达是多条关系，而不是复制三份图片或强行选一个父节点。

图片与概念关系建议分为：

- `expresses`：图片直接、主要表达该概念。
- `supports`：图片可以作为该概念的证明或背书。
- `visual_related`：画面相关，但不能单独证明该卖点。
- `excludes`：图片不应因相似词被该概念召回。

### 4.4 搜索表达主要复用在概念层

每个业务概念保存多种搜索表达：

- 标准名称。
- 官方简称和别称。
- 产品功能表达。
- 家长/学生痛点表达。
- 结果导向表达。
- 使用场景表达。
- 口语、省略说法和常见误写。

图片只补充自己独有的画面内容，例如“专家讲座现场”“孩子在书桌前拍练习册”“蓝色竖版学习报告”。

### 4.5 素材组是后台能力，不是上传负担

首次上传任意一张图时，后台自动创建只有一张图的素材组，设计师不需要感知“必须建立一组”。

后续如果出现：

- 横版、竖版、方图等尺寸延展；
- 同一主视觉的渠道适配；
- 备选版本；
- 替换后的新正式版本；

再从详情页追加即可。

判断规则：

- 仅裁切、排版、比例或渠道适配变化：作为延展版本，继承主图语义。
- 核心主体、画面含义或业务表达发生明显变化：作为新素材或新版本，重新分析。
- 延展图不存在时不展示空槽位，也不影响主图发布和搜索。

### 4.6 负责人审批是发布准入

建议素材状态：

- `draft`：未完成或未确认。
- `approved`：已由业务负责人审核通过。
- `published`：已进入业务搜索库。
- `retired`：不再用于普通搜索，但保留历史。

当前流程中上传图片通常已经在系统外完成审核，因此授权设计师可以上传即标记为 `approved/published`。系统不新增业务质量评分。

在发布准入之外，业务负责人还会确认图片与业务点之间的关系。这属于“语义关系认证”，不是再次审核图片好坏。负责人只需要判断候选关系：

- `expresses`：图片直接、主要表达该业务概念；
- `supports`：图片可以同时证明或支持该业务概念；
- `not_applicable`：候选业务概念不成立或容易造成误导。

负责人确认后的关系作为人工金标准写入 `asset_concept_links`，优先级高于 AI 建议。若负责人认为一张图的所有候选点均正确，系统应支持批量接受，不要求重新填写大量细词标签。

## 5. 目标数据模型

以下是目标结构，不要求一次性全部上线。

### 5.1 `business_concepts`

```text
id
code                    稳定唯一编码，改名时不改变
name                    当前展示名称
concept_type            product_function / user_pain / ...
definition              明确业务含义和边界
status                  draft / active / deprecated / merged
version
replaced_by_concept_id  合并或替代后的目标概念
created_at
updated_at
```

约束：

- 不物理删除已被图片或搜索日志引用的概念。
- 改名只改 `name`，不改 `code`。
- 合并/拆分必须保留迁移关系和变更记录。

### 5.2 `concept_system_links`

```text
concept_id
system_tag_id
role          core / support / evidence / related
weight        仅作排序初始信号，不作为永恒真理
reason
status
```

一条业务概念可以关联多个体系。

### 5.3 `concept_relations`

```text
source_concept_id
target_concept_id
relation_type   broader_than / narrower_than / supports /
                similar_to / distinguishes_from / conflicts_with
reason
status
```

典型用途：

- 专项培优 `broader_than` 重难点培优/考前突击/专项突破。
- AI 拍题精学 `distinguishes_from` 普通直接出答案搜题。
- 师资背书 `supports` 专家规划和新中考教研。

### 5.4 `concept_search_phrases`

```text
id
concept_id
phrase
phrase_type     official / alias / pain / outcome / scenario /
                colloquial / typo
origin          source_document / manual / ai / search_feedback
review_status   pending / accepted / rejected
weight
source_ref
created_at
```

这张表替代把大量完整句子塞进 `ContentTag` 的做法。

### 5.5 `asset_groups`

```text
id
title
primary_image_id
approval_status
publish_status
created_by
created_at
updated_at
```

一个素材组可以永远只有一张主图。

### 5.6 `images` 增量字段

保留现有 `images` 文件和存储结构，增量增加：

```text
asset_group_id
asset_role       primary / derivative / alternative / revision
width
height
aspect_ratio
channel          可空，如朋友圈/公众号/投放页
version_no
is_current
```

### 5.7 `asset_concept_links`

```text
id
asset_group_id
concept_id
relation_role    expresses / supports / visual_related / excludes
origin           manual / ai / migrated
review_status    pending / accepted / rejected
confidence
evidence_reason
source_ref
created_at
```

人工已确认关系权重高于 AI 待审核关系。

### 5.8 `asset_search_phrases`

保存仅对某一素材成立、不能复用到整个概念的搜索表达：

```text
id
asset_group_id
phrase
origin
review_status
weight
```

### 5.9 图片语义档案 V2

现有 `semantic_profile_json` 可以先升级结构，不急于拆成多张表：

```json
{
  "schema_version": 2,
  "visual_facts": [],
  "ocr_text": [],
  "subjects": [],
  "scenes": [],
  "actions": [],
  "visual_style": [],
  "visible_product_features": [],
  "asset_search_phrases": [],
  "negative_visual_concepts": []
}
```

客观画面事实和业务概念判断必须分开保存。AI 不得为了满足格式，强行在客观图片摘要里补写一个并不存在的卖点。

## 6. 现有代码的保留与改造判断

### 6.1 保留的基础能力

以下能力已经存在，继续使用：

- FastAPI、SQLAlchemy、Alembic 和现有仓储/服务分层。
- 图片上传、校验、存储、缩略图、下载、软删除和审计。
- 用户、角色、会话和权限体系。
- 模型 Provider 抽象和后台图片分析任务。
- Meilisearch 搜索索引与失败回退。
- Embedding 生成、保存和向量召回。
- Reranker 接口。
- 搜索日志、反馈和搜索运营后台。
- 六大体系现有稳定 code。

### 6.2 当前需要解决的结构问题

1. `UploadDialog.tsx` 强制选择主业务标签，导致没有强体系归属的图片被迫归类。
2. `ImageTaggingService` 要求图片至少有一个可打标标签。
3. `ImageBusinessLabel` 仍以固定 `Tag` 为中心，难以表达图片对多个可变业务概念的不同关系。
4. 人工“希望被搜到的话术”作为 `ContentTag.dimension = 用户预期搜索词` 保存，无法独立审核、版本化和观察效果。
5. 当前 AI 规则强制 `image_summary` 同时包含画面、功能、卖点和排除边界，容易把业务推测混成客观事实。
6. 当前 AI 强制生成 18-22 个内容标签，可能为了满足数量产生低价值近义词。
7. 当前 `images` 没有素材组、延展尺寸、替换版本和继承关系。
8. 当前业务端默认“精准搜索”，还要求用户理解精准/智能模式差异。
9. 智能搜索按“意图理解 → 召回 → Embedding → Reranker → 摘要 AI 裁判”串行累加，延迟和故障风险偏高。
10. 当前 50 条搜索评测主要验证六大体系和固定二级标签，缺少画面、口语、跨概念、应用场景和歧义查询。

### 6.3 现有结构到目标结构的映射

| 当前结构 | 过渡处理 | 目标结构 |
|---|---|---|
| `Tag(node_type=system)` | 保留稳定 code | 六大体系 |
| `Tag(node_type=image_label)` | 迁移为初始业务概念 | `business_concepts` |
| `ImageBusinessLabel` | 保留来源/审核/理由并迁移 | `asset_concept_links` |
| `ContentTag` | 保留客观内容词 | 图片语义词 |
| 用户预期搜索词 ContentTag | 拆出 | `asset_search_phrases` |
| `business_intents.json` | 迁移词组和边界 | 概念搜索表达与概念关系 |
| `ImageLevel2Category` | 兼容读取后逐步停用 | 业务概念关系 |
| 单张 `Image` | 每张旧图自动建一组 | `asset_groups + images` |
| 图片级搜索结果 | 兼容期同时返回 | 素材组级搜索结果 |

## 7. 设计师端目标流程

### 7.1 首次上传

必填：

- 图片文件。
- 图片名称，允许从文件名自动生成。

可选：

- 设计任务/原始需求。
- 这张图主要想表达什么。
- 这张素材独有的首次搜索话术，逐条添加且首次最多 5 条；发布后可持续补充，通用话术复用概念层表达。
- 使用渠道。

不再必填：

- 主业务标签。
- 延展尺寸。
- 20 个人工标签。
- 最终证明点定稿。

后台自动：

1. 创建素材组和主图记录。
2. 读取宽高和比例。
3. 执行 OCR 和视觉分析。
4. 生成客观语义档案。
5. 匹配业务概念并给出关系类型建议。
6. 生成图片独有搜索表达。
7. 生成/刷新 Embedding。
8. 同步搜索索引。

### 7.2 审核

设计师只需要审核高价值内容：

- 主要表达哪些业务概念。
- 可以支持哪些概念。
- 哪些相似概念应排除。
- AI 生成的少量图片独有搜索语是否合理。

不要求逐个审核大量客观词，也不要求每张图必须找到一个强业务归属。

业务负责人负责确认图片最终“主要表达/可以支持/不适用”的业务概念关系；设计师可以负责上传、整理和录入确认结果。审核界面应支持候选关系批量接受，避免负责人重复填写大量标签。

### 7.3 后续追加延展尺寸

入口位于素材详情页：`添加延展版本`。

流程：

1. 选择文件。
2. 系统识别尺寸和比例。
3. 只完成安全上传、缩略图与尺寸记录，不运行 AI 分析。
4. 直接继承素材组已有的业务关系和搜索表达，不新增或改写 AI 候选。
5. 发布后搜索结果仍只显示一个素材组。

### 7.4 替换主图

- 新图作为 `revision` 上传。
- 继承人工确认的业务概念关系作为待复核初始值。
- 重新执行视觉/OCR分析。
- 差异过大时提示拆成新素材。
- 切换 `primary_image_id` 后，旧图退为历史版本，不进入默认搜索。

## 8. 业务端目标流程

### 8.1 一个搜索框

业务用户不再选择“精准/智能”。系统自动判断查询属于：

- 明确体系/功能词。
- 产品模块。
- 用户痛点。
- 结果诉求。
- 师资/品牌背书。
- 画面内容或风格。
- 渠道/尺寸要求。
- 多意图或歧义表达。

六大体系仍可作为快捷入口和筛选项。

### 8.2 素材组级结果

结果卡片显示：

- 当前正式主图。
- 图片名称。
- 简短匹配原因。
- 主要表达/可以支持的业务概念。
- 已有尺寸数量。
- 下载或打开详情。

内部 S/A/B/C 分数可以保留用于评测和运营，不建议直接暴露给普通业务用户。

### 8.3 歧义查询

例如“家长省心”可能同时指：

- AI 自动制定学习方案。
- 真人老师督学。
- 家长查看学情周报。

系统不应武断地只留下一个固定标签。正确做法是：

- 返回跨概念的高相关结果；
- 在结果顶部给出“学习规划 / 真人督学 / 学情报告”意图缩小选项；
- 不阻塞用户先看到图片。

## 9. AI 和搜索基础设施职责

### 9.1 原则

> 上传时可以多分析，搜索时必须少等待；离线结果尽量预计算，在线模型必须可跳过。

### 9.2 上传阶段（异步）

可以使用：

- OCR：提取图片中真实文字。
- 视觉模型：生成客观画面事实、主体、场景、动作和风格。
- 生成式模型：根据当前业务概念库建议概念关系和图片独有搜索语。
- Embedding：生成图片语义文档向量，必要时增加多模态图片向量。
- Meilisearch：刷新关键词索引。

这些任务可以耗时，但必须是后台任务，并展示 `queued/running/succeeded/failed` 状态。

### 9.3 在线搜索阶段

在线链路拆成并行分支：

```text
本地词典/概念快速理解 ─┐
Meilisearch 关键词召回 ─┼─> 合并候选 ─> 一次重排 ─> 素材组去重 ─> 返回
Embedding 语义召回 ────┘
复杂查询模型理解 ──────┘（并行、可超时丢弃）
```

在线默认不再执行第二次生成式“图片摘要裁判”。其职责应合并到一次 Reranker，或者只在离线评测/极少数歧义场景启用。

### 9.4 模型使用策略

- 本地高置信命中标准概念时，不调用生成式查询理解。
- 常见查询结果缓存标准化查询和向量。
- 长句、痛点句和歧义句才调用生成式查询理解。
- 生成式查询理解与关键词/Embedding召回并行，不先等待它完成再开始召回。
- Reranker 只处理前 20 个候选。
- 所有模型返回必须经过结构校验和概念 code 校验。
- 模型失败时不得清空已有召回结果。

### 9.5 建议时间预算

具体数值需根据实际 Provider 压测调整，初始目标：

| 环节 | 目标预算 |
|---|---:|
| 本地标准化、概念匹配、缓存 | 50ms 内 |
| Meilisearch 召回 | 150ms 内 |
| 查询 Embedding | 1.8s 内；高置信本地概念查询跳过 |
| 复杂查询模型理解 | 900ms 内，且与召回并行 |
| Top 20 Reranker | 1.4s 内，且不得超过剩余总截止 |
| 常规查询端到端 | 1.5s 左右 |
| P95 硬目标 | 2.5s 内 |

总截止时间到达时立即返回已取得的最好结果，不继续等待慢接口。

### 9.6 降级矩阵

| 故障 | 仍然执行 |
|---|---|
| 生成式查询理解失败 | 本地概念理解 + 关键词 + Embedding + Reranker |
| Reranker 失败 | 本地融合评分排序 |
| Embedding 失败 | Meilisearch + 数据库概念/短语匹配 |
| Meilisearch 失败 | 数据库搜索 + Embedding |
| 所有外部模型失败 | 数据库精确/模糊搜索 + 概念词典扩展 |

## 10. 目标搜索算法

### 10.1 查询理解结果

内部统一成结构化 Query Profile：

```json
{
  "original_query": "",
  "normalized_query": "",
  "explicit_system_codes": [],
  "candidate_concepts": [],
  "pain_points": [],
  "desired_outcomes": [],
  "visual_constraints": [],
  "channel_or_size": [],
  "negative_constraints": [],
  "ambiguity": [],
  "confidence": 0.0
}
```

### 10.2 召回来源

1. 标准名称和稳定 code。
2. 已审核概念搜索语。
3. 图片独有搜索语。
4. OCR 文字。
5. 客观画面语义。
6. 概念之间的上位/下位/支撑/区别关系。
7. Embedding 语义相似。
8. 用户明确选择的体系、渠道和尺寸筛选。

### 10.3 排序可信度顺序

初始原则，不在缺少评测数据时过早固化具体百分比：

1. 明确命中的已审核概念名称或搜索表达。
2. 图片人工确认的 `expresses` 关系。
3. 图片人工确认的 `supports` 关系。
4. Reranker 对查询与图片语义的一致性判断。
5. OCR/客观画面事实匹配。
6. AI 已接受关系。
7. AI 待审核关系，仅作弱召回和弱排序信号。

以下条件可作为硬过滤：

- 素材未发布或已退役。
- 用户明确指定尺寸/渠道且素材不满足。
- 用户明确否定某概念。
- 图片与概念存在已确认 `excludes` 关系。

六大体系默认不作为硬过滤，除非用户明确选择体系筛选。

### 10.4 匹配解释

解释来自真实匹配链路，不由模型自由编写。例如：

```text
主要表达“AI拍题精学”
命中搜索表达“拍题后不是直接给答案”
图片可见“题目识别、分步提问、动画讲解”
```

## 11. 分阶段实施计划

### Phase 0：建立真实基线和冻结验收规则

启动门槛：

- 不要求全部正式图片到齐。
- 最小可以用 3-6 张已审核的代表图片启动，最好覆盖不同素材类型，如产品功能截图、人物/学习场景图、师资或数据背书图。
- 每张代表图需要有负责人确认的业务点；先准备与这些图片对应的 10-20 条搜索语即可。
- 如果暂时连代表图也没有，可以先整理概念种子和测试结构，但不进行高风险数据库主结构切换。

工作：

- 收集首批正式主图和真实业务查询。
- 接收业务负责人对每张图可证明业务点的确认结果；如果能区分，则额外记录“主要表达”和“可以支持”。
- 为每条查询标记强相关素材组、可接受素材组和禁止出现素材组。
- 运行当前版本搜索并保存 Top 结果、延迟和失败情况。
- 建立新的评测数据结构，不能只写抽象图片描述，必须逐步落到真实 asset/image ID。

退出条件：

- 至少有一批覆盖六大体系、痛点、结果、跨概念和歧义表达的真实查询。
- 能重复运行当前搜索并得到基线报告。

### Phase 1：引入可版本化业务概念层

工作：

- 增加 `business_concepts`、`concept_system_links`、`concept_relations`、`concept_search_phrases`。
- 将现有固定图片标签迁移为初始业务概念。
- 将 `business_intents.json` 的话术、痛点和排除项迁移为概念表达和关系。
- 保留旧标签 API 兼容读取。
- 增加概念管理和审核接口，UI 可后置。

退出条件：

- 同一个概念可以关联多个体系。
- 概念可以改名、停用、合并而不破坏历史图片和搜索日志。

### Phase 2：素材组和可选延展图

工作：

- 增加 `asset_groups` 和图片增量字段。
- 为每张旧图片自动创建一个素材组。
- 增加延展图/备选图/新版本上传接口。
- 搜索响应支持素材组级结果，兼容旧图片结构。

退出条件：

- 首次上传不要求延展图。
- 延展图可在任意时间追加并继承主图关系。
- 同组多个尺寸不重复占据搜索结果。

### Phase 3：拆分客观图片语义和业务关系

工作：

- 升级图片分析协议为 Semantic Profile V2。
- 接入 OCR 输出字段。
- 移除“必须生成 18-22 个标签”的硬要求，改为质量和覆盖维度校验。
- 图片客观描述不再强制写业务卖点。
- AI 业务判断写入 `asset_concept_links` 待审核建议。
- 用户预期搜索词迁移到独立素材搜索短语。

退出条件：

- 客观画面事实与业务概念建议能够分别审核和更新。
- 重跑 AI 不覆盖人工已确认关系和短语。

### Phase 4：重构在线搜索编排

工作：

- 搜索端点改为异步编排。
- 本地概念匹配、Meilisearch、Embedding 和复杂查询理解并行。
- 合并 Top 候选后只执行一次 Reranker。
- 摘要生成式裁判退出默认必经链路。
- 增加总截止时间、分阶段超时、缓存和降级监控。
- 排序以素材组为单位。

退出条件：

- 任一模型不可用时搜索仍有结果。
- P95 达到约定时间目标。
- 评测集中跨概念误判率明显低于当前基线。

### Phase 5：重构设计师端和业务端

设计师端：

- 简化首次上传。
- 主业务标签改为可选的业务意图/概念建议。
- 新增概念关系审核。
- 新增“添加延展版本”和“替换主图”。

业务端：

- 合并精准/智能为一个搜索框。
- 增加六大体系快捷筛选，但不强制使用。
- 素材组级展示和尺寸选择。
- 展示简洁匹配原因。
- 增加单结果“不相关/不是这个意思”反馈。

退出条件：

- 设计师可以只上传一张已经审核通过的主图并完成发布。
- 业务方不需要理解搜索模式或内部标签结构。

### Phase 6：迁移、双读验证和旧逻辑下线

## 12. 测试与验收

### 12.1 查询构成建议

- 25% 标准体系/产品功能词。
- 30% 家长或学生痛点表达。
- 20% 结果导向和口语表达。
- 15% 跨体系、相邻概念和歧义表达。
- 10% 画面、风格、渠道、尺寸和否定条件。

### 12.2 评测标注

每条查询至少保存：

- `strong_relevant_asset_ids`
- `acceptable_asset_ids`
- `forbidden_asset_ids`
- 期望概念。
- 可能歧义。
- 是否允许少结果。

### 12.3 建议验收目标

目标需在 Phase 0 基线后最终确认，初始建议：

- 明确概念查询 Top 3 命中率 ≥ 95%。
- 口语/痛点查询 Top 3 命中率 ≥ 85%。
- 禁止素材进入 Top 5 的比例 ≤ 5%。
- 已有合适素材时零结果率接近 0。
- 模型接口异常时，搜索仍在约定时间内返回降级结果。
- 搜索 P95 ≤ 2.5 秒。
- 同一素材组的延展尺寸不重复铺满结果页。

## 14. 已知风险与控制措施

| 风险 | 控制措施 |
|---|---|
| 下层证明点继续变化 | 概念稳定 code + 版本 + 合并/替代关系，不物理删除 |
| 一张图跨多个体系 | 多对多关系和关系角色，不强制唯一主体系 |
| AI 把业务推测当画面事实 | 客观语义与业务概念建议分离 |
| 模型接口不稳定 | 并行、硬超时、缓存和分级降级 |
| 标签/短语越来越多 | 概念级复用、来源审核、搜索效果反馈和停用机制 |
| 延展尺寸导致重复结果 | 素材组级召回和展示 |
| 更换图片需要重新打标 | 继承人工确认关系，差异分析后只复核变化 |
| 业务查询本身歧义 | 多概念召回 + 意图缩小选项，不强行伪造唯一答案 |
| 营销数字口径变化 | 证据版本化、保留来源和适用时间 |
| 大改影响测试版本 | 分阶段迁移、旧 API 兼容、双索引和可回滚开关 |
