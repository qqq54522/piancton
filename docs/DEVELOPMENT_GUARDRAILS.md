# 后续开发核心护栏

本文档用于后续 web coding 前快速确认方向：项目当前没有发现已经失控的重模块，但搜索链路、AI 打标规则和前端图片工作台会随着真实使用继续增长。后续优化要围绕真实评测推进，不能重新堆成补丁式代码。

## 一句话准则

新增能力必须先进正确边界，再谈实现细节；能放配置的不要写死在流程里，能放独立服务的不要塞回编排层，能用真实评测判断的不要只凭感觉改。

## 当前地基状态

- 架构边界已经清楚：API、Service、Domain、Repository、Storage、ModelProvider、Search backend 各有职责。
- Docker、本地检查和 GitHub PR 检查已经跑通，基础打包链路稳定。
- Meilisearch 是可选增强层和可重建派生索引，不是主数据库。
- Phase 4 已建立分层编排：`SearchService` 只装配，`AsyncSearchOrchestrator` 只串联，`SearchExternalBranches` 管理外部分支，`SearchRerankCoordinator` 管理唯一一次 Reranker。
- Phase 5 已完成两个使用端改造：普通业务端只有一个搜索框和显式可选的体系过滤；设计师端通过素材详情维护版本、概念关系和搜索话术。
- 版本化业务概念与人工确认的素材关系是可变业务语义的事实来源；`tags` 只保存六大体系稳定节点，旧标签树不再承担运行职责。
- 目前没有看到哪一块已经重到会拖垮后续开发。
- 后续风险主要来自功能继续变多时，把规则、流程和 UI 状态重新塞进少数大文件。

## 三块需要持续看住

### 1. 搜索链路

搜索相关逻辑可以继续优化，但不要把召回、理解、过滤、排序和响应组装重新混到一起。

- 查询理解放在 `query_understanding_service.py`。
- 业务话术和意图簇优先放在 `taxonomy/business_intents.json`。
- 数据库召回放在 `database_search_recall.py`。
- Meilisearch 召回放在 `meilisearch_recall_service.py`。
- Embedding 召回放在 `embedding_recall_service.py`。
- 显式体系限制放在 `search_system_filter.py`；已确认 `excludes` 关系由概念召回与排序边界处理，不再恢复旧强标签过滤器。
- 排序和打分放在 `search_ranking_service.py`、`search_scorer.py`。
- 响应拼装放在 `search_response_builder.py`。
- 流水线顺序和降级汇总放在 `search_orchestrator.py`；外部任务并发、分支预算、缓存与候选水合放在 `search_external_branches.py`；总截止和唯一一次重排放在 `search_rerank_coordinator.py`。不要把这些职责塞回单个召回服务或总入口。
- 外部并发召回先返回候选 ID/向量，ORM 实体只允许由请求主会话装载；不得跨线程共享 SQLAlchemy Session。
- 在线链路不得重新启用生成式图片摘要裁判；候选合并后最多执行一次 Top 20 Reranker。

需要新增搜索规则时，优先判断它属于“词库配置、召回、过滤、排序、展示”哪一类，不要直接改总入口。

### 2. AI 画面分析与业务概念

AI 可以补充客观内容标签和业务概念关系建议，但负责人确认、AI 建议和审核状态必须继续分清楚。

- 六大体系稳定 code 以体系源文件和 `tags` 六个节点为准；可变化业务概念、概念搜索表达和素材关系以数据库概念层为准。
- AI 输出必须经过 normalizer、schema 和 taxonomy 校验后才能写入。
- 人工事实与 AI 建议不能混用：继续保留 `origin=manual/ai` 和 `review_status=pending/accepted/rejected` 的边界。
- 新增打标规则时，优先沉淀到 taxonomy、skills 或独立规则服务，不要写成散落在上传流程里的特殊判断。
- 真实图片评测前，不要为了“看起来更聪明”重新引入图片直挂标签或固定二级树。

### 3. 前端图片工作台

图片首页、详情页、审核页会继续承载更多操作，是最容易变重的地方。新增 UI 时优先拆成组件和 hook。

- 数据请求和远程状态放在 `features/*` 的 hook 中。
- 页面文件只负责页面编排，不承接复杂业务判断。
- 图片卡片、上传弹窗、详情面板、AI 分析面板继续保持独立组件；六体系快捷筛选属于统一搜索组件，不新建旧标签筛选弹窗。
- 素材组查询与 mutation 继续集中在 `features/assets`；版本维护、概念关系审核、搜索话术审核和素材组结果卡不得重新合并成一个工作台大组件。
- 普通业务端不得重新暴露 `precise/smart/configured` 内部模式；六大体系只有在用户显式选择时才进入后端硬过滤。
- 单结果反馈只写搜索反馈目标，不得从前端直接修改素材审批或人工概念关系。
- API 字段变化后同步生成或更新前端类型，不要用临时 `any` 绕过去。
- 新增复杂交互时，先确认已有组件能否复用，再决定是否新建组件。

## 判断模块是否开始变重

出现以下情况时，先停下来拆边界，再继续加功能：

- 一个文件同时处理 HTTP、业务规则、数据库查询和响应拼装。
- 一个函数需要同时理解搜索意图、查库、调用外部服务、排序和格式化结果。
- 新需求只能通过不断追加 `if/else` 特判完成。
- 配置、业务话术或概念规则散落在多个代码文件里。
- 前端页面文件开始同时管理请求、表单、弹窗、权限、筛选、展示和副作用。
- 测试只能靠跑完整流程才能覆盖一个很小的规则。

## 后续优化顺序

1. 先用真实图片跑上传、AI 分析、人工修正、搜索、下载的完整闭环。
2. 再根据搜索评测结果优化业务话术、召回、过滤和排序。
3. 再根据真实打标误差优化 taxonomy、AI 提示词和审核流程。
4. 当上传或 AI 分析明显变慢，再把 `BackgroundTasks` 升级为独立 worker。
5. 当本地质量稳定后，再接对象存储、备份恢复、云服务器和 CI/CD 发布链路。

## 暂时不要提前做的事

- 不要在真实评测前大改数据库主结构。
- 不要把 Meilisearch 当成唯一搜索事实源。
- 不要为了未来云端部署，把本地开发流程改复杂。
- 不要提前接对象存储、备份系统和云服务，除非已经完成真实业务闭环。
- 不要把 AI 结果直接当成人工确认结果。
- 不要用新大文件承接所有“临时规则”。

## 每次改动前的检查

动代码前先问这五个问题：

1. 这个逻辑属于 API、Service、Domain、Repository、前端 hook，还是组件？
2. 这个规则能不能放进 taxonomy、skills 或配置文件？
3. 这个改动有没有破坏负责人确认关系、AI 建议和审核状态的边界？
4. 这个搜索优化能不能被 `taxonomy/search_eval_cases.json` 或真实样本验证？
5. 这个前端改动会不会让页面文件重新变成大杂烩？

如果五个问题里有两个以上答不上来，先不要继续堆代码，先拆清楚边界。

## 当前可安心推进的方向

Phase 6 旧职责已经下线。现在可以把主要精力放在真实素材闭环：逐步导入代表素材，观察 AI 概念建议、负责人修正、搜索命中和业务人员反馈，再用新数据重建 Phase 0/4 基线。只要继续遵守本文档的边界，后续优化不会天然给项目造成很大负担。
